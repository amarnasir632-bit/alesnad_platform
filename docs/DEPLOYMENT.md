# خطة نشر منصة الإسناد الأكاديمي

هذه الخطة تسجل المعمارية التي اعتمدها مالك المشروع، وتفصلها عن إعدادات الإنتاج التي لم تعتمد بعد. لا تعتبر المنصة جاهزة للنشر العام لمجرد إنشاء الخادم أو تطبيق ترحيلات قاعدة البيانات.

## المعمارية المستهدفة

- التطبيق: PHP 8.4+ وواجهة PHP/PDO، مع web root على `public/` فقط.
- قاعدة البيانات: PostgreSQL على خادم التطبيق أولًا، مع إبقاء خيار فصلها على خادم خاص لاحقًا.
- DNS وحماية الموقع: Cloudflare.
- الحصص المباشرة والتسجيلات: Cloudflare Stream. قرر المالك دخول النوعين في الإطلاق؛ يجب استخدام Live Inputs مع التسجيل التلقائي والحماية بروابط موقعة بعد التحقق من صلاحية المستخدم في backend.
- النسخ: تخزين خارجي مستقل عن خادم التطبيق وقاعدة الإنتاج؛ لم يُحسم المزود أو الحساب/النطاق الإداري أو مدة الاحتفاظ.

لا تُخزّن مفاتيح Cloudflare أو كلمات مرور قاعدة البيانات في الشيفرة أو Git. تضبط أسرار Stream في إعدادات الخادم فقط.

## ما يمنع إطلاق الموقع للعامة حاليًا

1. لم تكتمل بعد مراجعة جميع متطلبات SRS وإثباتها على PostgreSQL فعلي. توجد إدارة صفوف ومواد ومحتوى وأسئلة واختبارات وحصص ورسائل عبر صفحات/API، وتحتاج اختبارات تكامل وقبول قبل الإطلاق.
2. أضيفت آلية backend لمنح/سحب الوصول اليدوي وسجلها؛ يجب التحقق من ترحيلها وتطبيق صلاحياتها على PostgreSQL فعلي قبل اعتمادها. إخفاء عناصر الواجهة وحده لا يحمي المحتوى.
3. أضيف تكامل Cloudflare Stream لـLive Inputs، مفاتيح إرسال تعرض مرة واحدة للأستاذ، إصدار روابط تشغيل موقعة، ومزامنة التسجيلات الجاهزة. لا يمكن التحقق من التكامل دون أسرار حساب Cloudflare وبث تجريبي. أعداد التزامن ما زالت غير معروفة.
4. لم تصل سياسة الخصوصية والاستخدام بعد، ولا توجد واجهات إقرار/موافقة مرتبطة بها.
5. أعداد الحصص المتزامنة والاستخدام المتوقع غير معروفة؛ لذلك لم تُعتمد حدود الفيديو أو خطة الخادم، ولم تُحدد قيم RPO/RTO.
6. لم تُنفذ النسخ الاحتياطية المجدولة خارج الخادم أو تمرين استعادة موثق.
7. واجهة إدارة الحصص تستخدم API الحالي، لكن صفحات SRS الأخرى لا تزال تحتاج جولة تحقق عبر المتصفح وربط فعلي لكل إجراء؛ فحص صياغة PHP وحده لا يثبت سلامة الواجهة أو النشر.

## إعداد الخادم عند اعتماده

1. إعداد نظام مدعوم، PHP 8.4+ مع `pdo_pgsql` وPDO و`fileinfo` و`mbstring`، PostgreSQL، وخادم ويب PHP-FPM أو ما يعادله.
2. ضبط web root على مجلد `public/`. يجب ألا يستطيع الويب تقديم `.env` أو `database/` أو `app/` أو `storage/`.
3. إعداد Nginx/Apache لإرسال المسارات غير الثابتة إلى `public/index.php`، ومنع الوصول إلى الملفات المخفية، وتعطيل عرض أخطاء PHP للزوار.
4. تثبيت شهادة TLS صالحة على الأصل قبل ضبط Cloudflare على Full (strict). تعطيل التخزين المؤقت لصفحات الجلسات والنماذج والمحتوى الخاص.
5. إنشاء قاعدة PostgreSQL ومستخدم تطبيق محدود الصلاحية. يفضّل فصل صلاحية ترحيل المخطط عن صلاحيات مستخدم وقت التشغيل قبل الإنتاج.
6. وضع `.env` على الخادم خارج web root، وضبط `APP_ENV=production` و`APP_DEBUG=0` و`APP_URL` و`SESSION_SECURE=1` وبيانات PostgreSQL. لا يُنسخ `.env.example` كما هو إلى الإنتاج.
7. تشغيل جميع الترحيلات المتاحة من `001` إلى `010` مرة واحدة بإجراء نشر مضبوط، ثم إنشاء حساب مدير أول من طرفية الخادم التفاعلية؛ لا تُنشأ كلمة مرور افتراضية. أُثبت تطبيق ملفات الترحيل الـ14 المتاحة حتى `010` على قاعدة التطوير المحلية `alesnad_platform`، كما تأكد تسجيل الدخول محليًا وفتح صفحة إدارة المنهج بحساب المدير. الكتالوج ما زال فارغًا وينتظر إدخال المراحل والصفوف والمواد يدويًا. هذا يثبت نجاح الترحيل والدخول المحلي فقط؛ اختبارات التكامل على قاعدة اختبار مستقلة وبيئة staging/production ما زالت مطلوبة.
   في فحص آمن لـ`.env` المحلي، وُجدت إعدادات الاتصال والمصادقة والرفع والاختبارات والرسائل بصيغ صالحة، والملف مستثنى من Git. إعدادات اعتماد Cloudflare Stream وقيم الاحتفاظ بسجلات التدقيق ومحاولات الدخول ما زالت فارغة؛ لا تُنقل قيم التطوير إلى الإنتاج.
8. إنشاء مجلد التخزين الخاص بصلاحيات قراءة/كتابة لمستخدم PHP-FPM فقط، خارج `public/`.
   إعداد `PRIVATE_STORAGE_PATH` و`UPLOAD_MAX_BYTES` المعتمد، والتأكد أن `upload_max_filesize` و`post_max_size` في PHP لا تقل عن الحد المعتمد. الرفع الحالي يقبل PDF فقط أو رابط HTTPS للموارد، ويخزن الملفات المرفوعة خارج web root.
9. إعداد النسخ الاحتياطي المشفر والمجدول إلى وجهة خارجية، والتحقق من checksum، والاحتفاظ بنسخ معزولة، ثم تجربة الاستعادة على قاعدة منفصلة قبل الإطلاق.
10. جدولة `php database/process_expired_quiz_attempts.php` كل دقيقة تحت مستخدم التطبيق حتى تتحول المحاولات المنتهية إلى `INCOMPLETE` في وقتها؛ يمكن تشغيله يدويًا محليًا للتحقق.
10. اختبار TLS وDNS، الدخول والخروج وCSRF، الصلاحيات السلبية والإيجابية، صفحات الخطأ، الملفات الخاصة، النسخ والاستعادة، ومراقبة سجلات PHP وPostgreSQL.

## متغيرات الإعداد

المتغيرات الأساسية موثقة في `.env.example`. لتفعيل Cloudflare Stream اضبط `STREAM_PROVIDER=cloudflare_stream` و`CLOUDFLARE_ACCOUNT_ID` و`CLOUDFLARE_API_TOKEN` بصلاحيات Stream Read/Write و`CLOUDFLARE_STREAM_CUSTOMER_CODE`. لا تحفظ مفتاح الإرسال الذي يصدره Stream في قاعدة المنصة؛ يظهر للأستاذ عند تجهيز مدخل البث مرة واحدة. لا توضع رموز API أو مفاتيح تخزين داخل `APP_URL` أو ملفات عامة.

## شروط اعتماد الإطلاق

- التأكد من أن المدير يستطيع إدخال الصفوف والمواد المطلوبة يدويًا على قاعدة الإنتاج؛ لا توجد قائمة مواد مزروعة افتراضيًا.
- تسجيل الطالب ذاتي، ومنح/سحب الوصول للمحتوى يدوي من المدير أو المراجع؛ يحتاج اختبارًا تكامليًا على PostgreSQL.
- ضبط `APP_URL` على عنوان HTTPS الفعلي؛ تستخدمه دعوات الفريق التي تنتهي بعد 48 ساعة. أرسل الرابط للموظف عبر قناة خاصة موثوقة.
- رابط الدعوة يحمل رمزًا سريًا في query string؛ اجعل سجلات الويب والخادم خاصة ومحدودة الاحتفاظ، ولا تضف أدوات تحليلات خارجية لصفحة قبول الدعوة.
- اختبار مصفوفة صلاحيات المدير ومراجع المحتوى وحسابات الفريق على قاعدة PostgreSQL.
- ضبط واعتماد سياسات الاختبارات (`QUIZ_MAX_ATTEMPTS`, `QUIZ_DURATION_MINUTES`, `QUIZ_RESULT_VISIBILITY`, `QUIZ_INCOMPLETE_ATTEMPT_POLICY`). بدء المحاولات متوقف بأمان حتى تُضبط القيم المطلوبة؛ يجب إضافة ضبط نافذة الاختبار إلى الواجهة.
- تسليم سياسات الخصوصية والاستخدام وإقرارها داخل الموقع.
- اعتماد خطة الاستضافة والأحمال وحدود الفيديو وتكلفة Cloudflare Stream، وسياسة الاحتفاظ بالتسجيلات.
- ضبط واختبار حساب Cloudflare Stream وصلاحيات API والبث الفعلي من برنامج مثل OBS، ثم التحقق من ظهور التسجيل ومشاهدته برابط موقع. البث التجريبي غير ممكن دون بيانات الحساب.
- اعتماد مدة الاحتفاظ بالرسائل وإجراءات الحذف والإشراف ضمن سياسة الخصوصية والاستخدام.
- اعتماد النسخ وRPO/RTO، وإثبات نجاح استعادة فعلية.
- مراجعة صفحات الموقع عبر متصفح واختبار إجراءاتها على نسخة ما قبل الإنتاج. مسارات نموذج الاختبار تستخدم خدمات التحقق الحديثة، بينما بيانات العرض في بعض الصفحات ما زالت تقرأ عبر طبقة PHP القديمة.
- استكمال وظائف SRS ذات أولوية الإطلاق واجتياز اختبارات القبول والصلاحيات على نسخة ما قبل الإنتاج.
