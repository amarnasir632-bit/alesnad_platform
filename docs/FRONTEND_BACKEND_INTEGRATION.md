# دليل ربط الواجهة الأمامية بالخلفية

هذا الدليل لفريقي الواجهة والخلفية في منصة الإسناد الأكاديمي. يوضح طريقة عمل المكونات، حدود المسؤولية، وتسلسل الربط حتى يستطيع الفريقان التطوير بالتوازي دون افتراض بيانات أو صلاحيات غير موجودة.

## 1. الصورة العامة

المتصفح يعرض واجهة عربية متجاوبة باتجاه RTL. الواجهة الأمامية مسؤولة عن العرض والتنقل وتجربة الاستخدام والتحقق الأولي من المدخلات. الخادم مكتوب بـ PHP ويقدم نقاط JSON تحت `/api/v1/`؛ وهو المسؤول عن التحقق النهائي، الجلسات وCSRF والصلاحيات وقواعد الأعمال. PostgreSQL يخزن البيانات، ويتصل به PHP عبر PDO.

```text
المتصفح (HTML/CSS/JavaScript)
        │ طلبات HTTP وJSON + Cookie الجلسة + CSRF
        ▼
PHP Router → Controllers → Services → PostgreSQL
        │ استجابات JSON أو تدفق ملف مصرح به
        ▼
المتصفح
```

لا تتصل الواجهة بقاعدة البيانات مباشرة، ولا تضع قواعد الصلاحية أو أسرار النظام داخل JavaScript. إخفاء زر في الواجهة يحسن التجربة فقط؛ قرار السماح أو الرفض يظل في الخادم.

## 2. أين يعمل كل فريق؟

| الفريق | ملكية الملفات | مسؤولياته |
| --- | --- | --- |
| الواجهة | `app/Views/` و`public/assets/` | الصفحات والمكونات، RTL والاستجابة للهاتف، حالات التحميل والفراغ والخطأ، استدعاء API وعرض النتائج. |
| الخلفية | `app/Http/` و`app/Services/` و`app/Auth/` و`app/Security/` و`app/Database/` و`database/` | المسارات، التحقق والصلاحيات، قواعد الأعمال، الاستعلامات والترحيلات، شكل JSON وسجلات التدقيق. |
| مشتركة | `docs/API_CONTRACT.md` و`docs/OPEN_DECISIONS.md` و`docs/TRACEABILITY.md` | الاتفاق على الحقول، الصلاحيات، الأخطاء، القرارات، والاختبارات قبل تغيير عقد مستخدم. |

يجب ألا يغير فريق الواجهة مخطط قاعدة البيانات أو ينفذ استعلامات SQL من المتصفح. ويجب ألا يغير فريق الخلفية شكل استجابة تعتمد عليه الواجهة دون تحديث `docs/API_CONTRACT.md` وإبلاغ الفريق الآخر.

## 3. ابدأ من عقد API

المرجع الدقيق لكل مسار هو [`API_CONTRACT.md`](API_CONTRACT.md). لكل ميزة، اتفقا قبل التنفيذ على:

1. المسار وطريقة HTTP.
2. الحقول المطلوبة والاختيارية وأنواعها.
3. شكل الاستجابة الناجحة والأخطاء المتوقعة.
4. من يستطيع القراءة أو الإنشاء أو التعديل.
5. حالات التحميل والفراغ وعدم الصلاحية وانتهاء الجلسة.
6. اختبار عقد بسيط يثبت أن طلب الواجهة واستجابة الخادم متوافقان.

كل الاستجابات المعتادة تتبع غلافًا مثل `{"data": ...}`. الخطأ يتبع `{"error":{"code":"...","message":"..."}}`. تعامل الواجهة مع `error.code` للقرار البرمجي، واعرض `message` للمستخدم عند ملاءمته. لا تعتمد على نص الرسالة لتحديد نوع الخطأ.

## 4. إعداد التشغيل والتطوير

الخلفية المحلية تعمل عبر خادم PHP من مجلد المشروع:

```bash
php -S 127.0.0.1:8000 -t public public/router.php
```

يجب أن تكون PostgreSQL والترحيلات وإعدادات `.env` جاهزة أولًا وفق `README.md`. افتح الواجهة والخلفية على الأصل نفسه (`http://127.0.0.1:8000`) لتستفيد الواجهة من Cookie الجلسة دون إعداد CORS. عند تطوير الواجهة على خادم منفصل، استخدم proxy تطوير يمرر `/api` إلى الخلفية مع الحفاظ على Cookie، أو نسقوا إعداد CORS وخصائص Cookie مع فريق الخلفية. لا تضف `Access-Control-Allow-Origin: *` مع بيانات اعتماد.

عنوان API النسبي هو `/api/v1`؛ استخدم مسارات نسبية بدل تثبيت عنوان جهاز مطور داخل ملفات الواجهة. لا تحط أسرارًا أو كلمات مرور أو مفاتيح مزود في إعدادات المتصفح.

## 5. الجلسة وCSRF: التسلسل المطلوب

المصادقة تعتمد جلسة متصفح وخادم، وليست Bearer token أو تخزين JWT في `localStorage`.

1. عند بدء التطبيق، استدعِ `GET /api/v1/csrf` مع `credentials: "same-origin"` واحفظ الرمز في ذاكرة التطبيق.
2. افحص الجلسة عبر `GET /api/v1/auth/me`. نجاحه يعيد المستخدم والأدوار؛ `401` يعني أن المستخدم غير مسجل أو أن الجلسة انتهت.
3. أرسل `X-CSRF-Token` في كل `POST`, `PUT`, `PATCH`, `DELETE`، مع Cookie الجلسة. بعد الدخول أو التسجيل أو الخروج، استخدم رمز CSRF الجديد الذي تعيده الاستجابة.
4. عند `419 csrf_failed`، اجلب رمزًا جديدًا مرة واحدة ثم أعد المحاولة الآمنة إذا لم تكن العملية قد تمت. تجنب إعادة إرسال عمليات الإنشاء بلا تحقق؛ الأفضل أن يرجع المستخدم للصفحة أو يتحقق من حالة السجل أولًا.
5. عند `401`, أعد الواجهة إلى الدخول وامسح بيانات المستخدم المؤقتة من الذاكرة. عند `403`, اعرض منع الوصول دون محاولة استنتاج صلاحيات المستخدم من الواجهة.

مثال مساعد JavaScript صغير:

```js
const API = "/api/v1";
let csrfToken = null;

async function refreshCsrf() {
  const response = await fetch(`${API}/csrf`, {
    credentials: "same-origin",
    headers: { Accept: "application/json" },
  });
  const payload = await response.json();
  if (!response.ok) throw new Error(payload?.error?.code ?? "request_failed");
  csrfToken = payload.data.csrf_token;
  return csrfToken;
}

async function apiRequest(path, { method = "GET", body, headers = {} } = {}) {
  const mutating = !["GET", "HEAD", "OPTIONS"].includes(method.toUpperCase());
  if (mutating && !csrfToken) await refreshCsrf();

  const requestHeaders = { Accept: "application/json", ...headers };
  if (body !== undefined && !(body instanceof FormData)) {
    requestHeaders["Content-Type"] = "application/json";
  }
  if (mutating) requestHeaders["X-CSRF-Token"] = csrfToken;

  const response = await fetch(`${API}${path}`, {
    method,
    credentials: "same-origin",
    headers: requestHeaders,
    body: body === undefined ? undefined : body instanceof FormData ? body : JSON.stringify(body),
  });
  const payload = response.status === 204 ? null : await response.json();
  if (!response.ok) {
    const error = new Error(payload?.error?.message ?? "تعذر تنفيذ الطلب.");
    error.status = response.status;
    error.code = payload?.error?.code;
    throw error;
  }
  if (payload?.data?.csrf_token) csrfToken = payload.data.csrf_token;
  return payload?.data;
}
```

هذا مثال أساس يحتاج أن يختبره الفريق مع المتصفح وإعدادات النشر. عند الرفع بـ`FormData` لا تضع `Content-Type` يدويًا؛ المتصفح يضيف boundary المطلوب. لا تطبع بيانات الدخول أو Cookie أو CSRF في سجلات المتصفح.

## 6. ترتيب الربط المقترح

نفذوا شريحة صغيرة كاملة من الشاشة إلى قاعدة البيانات، ثم انتقلوا لما بعدها:

1. **جلسة الدخول:** جلب CSRF، `auth/me`، الدخول والخروج والتسجيل كطالب. اتفقوا على توجيه المستخدم حسب الأدوار التي يعيدها الخادم.
2. **الاستكشاف الدراسي:** المراحل، الصفوف، المواد، الدروس المنشورة، ثم البحث. اختبروا حالات عدم وجود صفوف للمرحلة المتوسطة دون اختراع أسماء.
3. **المحتوى والاشتراك:** عرض نتائج البحث، حالة الاشتراك، ثم التنزيل المحمي. الملفات الخاصة لا تستخدم لها روابط عامة أو مسارات من `storage/`؛ استخدم endpoint التنزيل الذي يعيد الملف بعد التحقق.
4. **الأستاذ والإدارة:** الإسنادات، إدارة الهيكل الدراسي والحسابات، رفع الموارد والأسئلة ثم إرسالها للمراجعة. افصلوا نموذج المسودة عن إجراء الإرسال.
5. **الاختبارات:** قائمة الاختبارات المنشورة، بدء المحاولة، حفظ الإجابات، الإرسال ثم النتيجة. الخادم هو المرجع للوقت والمحاولات والنتائج.
6. **الحصص والرسائل:** قائمة الحصص والانضمام والرسائل الفردية. لا تعرضوا رابط الحصة إلا من استجابة endpoint الانضمام المخول. لا توجد مجموعات.
7. **اشتراكات الإدارة:** إدارة الخطط والاشتراكات يدويًا. لا تضيفوا شاشة دفع إلكتروني أو أسعارًا افتراضية؛ بوابة الدفع والأسعار والعملة قرارات مفتوحة.

راجعوا `API_CONTRACT.md` لتفاصيل الحقول والأدوار وحالات الخطأ لكل مجموعة. الخادم قد يعيد `503` عندما تكون قيمة إعداد لازمة غير محددة؛ اعرضوا حالة مفهومة للمستخدم وسجلوا الكود للفريق دون كشف إعدادات سرية.

## 7. أنماط واجهة تساعد على الربط

- ابنوا طبقة API واحدة تتعامل مع `fetch`, Cookie الجلسة، CSRF، JSON، وتحويل الخطأ. لا تكرروا هذه التفاصيل في كل صفحة.
- عرّفوا أنواع البيانات أو JSDoc للاستجابات الأساسية مثل `User`, `Stage`, `Subject`, `Resource`, `Quiz` و`ApiError`.
- لكل شاشة حددوا حالات `loading`, `success`, `empty`, `error`, `unauthenticated`, و`forbidden`.
- استخدموا `AbortController` لإلغاء البحث السابق عند إدخال استعلام جديد، مع تأخير قصير للبحث لتقليل الطلبات في الشبكات الضعيفة.
- اعرضوا أخطاء التحقق بجوار الحقل واربطوها بحالة `422`. لا تعتمدوا على تحقق المتصفح وحده.
- استخدموا ترقيم الصفحات (`limit` و`offset`) للمجموعات الكبيرة بدل تنزيل كل السجلات مرة واحدة.
- حافظوا على الروابط النسبية والأصول المحلية، واضغطوا الصور، وتجنبوا إعادة جلب القوائم دون حاجة.
- استخدموا عناصر HTML دلالية، تسميات حقول واضحة، تنقل لوحة مفاتيح، تباين مناسب، ورسائل عربية مفهومة. اضبطوا `lang="ar"` و`dir="rtl"` على المستند.
- لا تخزنوا ملفًا خاصًا في cache عام أو service worker. تعاملوا مع استجابات التنزيل على أنها خاصة بالمستخدم.

## 8. مسارات الملفات والتغييرات المشتركة

قبل بدء المهمة، سجلوا في Issue: اسم الشاشة، endpoint، المسؤول، الحقول، وحالات الخطأ. يفضل أن يعمل الفريقان على فروع منفصلة؛ ادمجوا تغييرات العقد أولًا أو بالتنسيق المباشر قبل بناء اعتماد طويل عليها.

إذا احتاجت الواجهة حقلًا غير موجود:

1. يطلب فريق الواجهة الحقل مع سبب استخدامه ومثال الاستجابة المطلوبة.
2. يتحقق فريق الخلفية من مصدر البيانات والصلاحية وعدم تسريب بيانات حساسة.
3. يحدث الفريقان `API_CONTRACT.md` ثم ينفذان التغيير كل في ملفاته.
4. يراجع الطرف الآخر الـ Pull Request المشترك ويجرب تدفقًا ناجحًا وحالة رفض.

لا ترفعوا `.env`, ملفات الطلاب، ملفات الرفع الخاصة، dump قاعدة البيانات أو نسخ `storage/backups` إلى GitHub.

## 9. اختبار التكامل وقبول الميزة

لكل تدفق واجهة، تحققوا من:

- الاستجابة الناجحة وعرض البيانات العربية وRTL.
- البيانات الفارغة والمدخلات غير الصالحة (`422`).
- انتهاء الجلسة (`401`) وغياب الصلاحية (`403`) وCSRF غير الصالح (`419`).
- انقطاع الشبكة أو `5xx` مع إمكانية إعادة المحاولة دون تكرار عملية حساسة.
- التأكد من أن الواجهة لا تعرض بيانات أو رابط ملف لا يعيده الخادم للمستخدم المخول.
- اختبار الهاتف، التنقل بلوحة المفاتيح، وحجم الشبكة المحدود.

الخلفية تملك اختبارات قواعد البيانات والصلاحيات وAPI؛ الواجهة تضيف اختبارات سلوك المكونات وتدفقات المستخدم، ثم يجرب الفريقان التدفق الكامل من المتصفح إلى PostgreSQL. نجاح اختبار endpoint وحده لا يثبت اكتمال الشاشة أو تجربة المستخدم.

قبل اعتبار الميزة جاهزة، يجب أن يكون عقدها محدثًا، حالات النجاح والرفض مجربة، القرار المعلق مسجلًا عند الحاجة، و`TRACEABILITY.md` محدثًا بما تم اختباره فعلًا. نتائج CI يجب أن تذكر بوضوح ما إذا كانت محلية أو صادرة من GitHub Actions.
