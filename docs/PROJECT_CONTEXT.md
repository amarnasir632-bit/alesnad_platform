# سياق منصة الإسناد الأكاديمي

هذا الملف مرجع أساسي للمطورين ومساعدات الذكاء الاصطناعي. اقرأه قبل تعديل النظام. يميز بين ما قرره مالك المشروع، وما صُمم في قاعدة البيانات، وما نُفذ في التطبيق، وما بقي ضمن خطة التطوير. لا تعتبر المتطلب منفذًا لمجرد وروده في BRD أو SRS.

## 1. تعريف المنتج والجهة

- **الاسم التجاري:** منصة الإسناد الأكاديمي.
- **الجهة المشرفة والمنفذة:** AL WARITH (الوارث).
- **الشعار:** `public/assets/brand/al-warith-logo.jpg`.
- **السوق والمنهج:** السودان والمنهج السوداني.
- **نوع المنتج:** منصة ويب تعليمية عربية تجمع المواد والدروس والموارد وبنك الأسئلة والاختبارات والحصص والرسائل.
- **المستخدمون:** الطالب، الأستاذ، مدير النظام/الأدمن، ومراجع المحتوى. ولي الأمر خارج النطاق الأولي ما لم يعتمد لاحقًا.
- **القيمة:** توفير وصول منظم للمحتوى والتقييم والتواصل، مع واجهة عربية RTL واهتمام بالهاتف والاتصال المحدود.

## 2. مصدر الحقيقة

1. آخر قرار صريح من مالك المشروع يحسم المتطلبات والقرارات التجارية.
2. BRD وSRS الإصداران 1.0 يصفان النطاق المقترح، وهما مسودتان تتطلبان اعتماد القرارات المفتوحة.
3. ترحيلات SQL والشيفرة الفعلية تحددان ما أُعد أو نُفذ تقنيًا.
4. `SqlDigram/` مرجع بصري أولي؛ المخطط التنفيذي في `database/migrations/` هو مصدر بنية PostgreSQL.
5. لا تخلط بين «مخطط له» و«منفذ» أو بين قرار مالك المشروع والقرار الفني الذي ما زال بانتظار التنفيذ.

## 3. التقنية والمعمارية المعتمدتان

- **Frontend:** HTML5 وCSS3 وJavaScript ES6+.
- **Backend:** PHP 8.4 أو أحدث متوافق.
- **Database:** PostgreSQL.
- **اتصال قاعدة البيانات:** PDO باستخدام `pdo_pgsql` واستعلامات محضرة.
- **الواجهة:** قوالب PHP وخدمات الخادم، عربية RTL ومتجاوبة.
- **تبادل البيانات:** JSON عند بناء API؛ صفحات الويب الحالية خادمية.
- **الإطار:** لا يفرض BRD/SRS إطار PHP بعينه؛ التنفيذ الحالي PHP أصلي دون إطار.
- **الوقت المحلي:** `Africa/Khartoum`، وتخزن الأوقات في PostgreSQL مع المنطقة الزمنية.

احفظ كلمات المرور عبر `password_hash()` وتحقق منها بـ`password_verify()`. لا تخزن كلمات المرور أو تفاصيل بطاقات الدفع بنص واضح. الأسرار وإعدادات الاتصال في `.env` غير المتعقب في Git. التحقق من الهوية والصلاحية يجب أن يتم على الخادم، وليس في JavaScript وحده.

## 5. نطاق المنتج

### المرحلة الأولى المستهدفة

- حسابات وتسجيل دخول وأدوار وصلاحيات للطالب والأستاذ ومدير النظام ومراجع المحتوى.
- إدارة المراحل والصفوف والمواد والدروس والتصنيفات.
- مكتبة موارد وكتب قابلة للبحث والتنزيل حسب صلاحيات الوصول اليدوية وحقوق النشر.
- رفع الأستاذ للمحتوى ومراجعته من الأدمن قبل النشر.
- بنك أسئلة مصنف حسب المادة والدرس والنوع والصعوبة.
- أرشيف امتحانات سابقة.
- اختبارات إلكترونية أساسية، تصحيح تلقائي للأسئلة الموضوعية، ونتائج للطالب والأستاذ المخول.
- جدولة الحصص، ربط مزود بث، وإتاحة التسجيلات بعد انتهاء الحصة حسب الصلاحية.
- رسائل فردية بين الطالب والأستاذ فقط.
- منح وسحب الوصول للمحتوى يدويًا؛ لا توجد بوابة دفع ضمن الإطلاق الحالي.
- لوحة إدارة للحسابات والمواد والمحتوى والأسئلة والامتحانات.
- واجهة عربية RTL، متجاوبة، ومراعية لتقليل استهلاك البيانات.

### لاحق أو مشروط

توليد الأسئلة بالذكاء الاصطناعي، الألعاب التعليمية، بوابة ولي الأمر، تطبيق جوال مستقل، التقارير المتقدمة، الشهادات، الإشعارات الموسعة، وإضافات المراحل. كل ميزة تحتاج اعتماد نطاق وتكلفة قبل بدء تنفيذها.

### خارج النطاق ما لم يعتمد لاحقًا

إنتاج جميع الكتب والفيديوهات من الصفر، العمل الكامل دون اتصال، سعة أو سرعة غير محدودة، التصحيح الآلي الكامل للمقالي، والدفع قبل تحديد مزود الخدمة ومتطلباته.

## 6. قاعدة البيانات

### الترحيلات

- `database/migrations/001_initial_schema.sql`: ينشئ مخطط PostgreSQL والجداول والعلاقات والقيود والفهارس.
- `database/migrations/002_seed_access_control.sql`: يضيف أدوار الطالب والأستاذ ومراجع المحتوى ومدير النظام، والصلاحيات وربطها بالأدوار.
- `database/migrations/003_seed_initial_academic_structure.sql`: يضيف المراحل الابتدائية والمتوسطة والثانوية والصف السادس والثالث الثانوي، وفق نطاق الإطلاق المبدئي.
- `database/migrations/004_auth_security.sql`: يضيف جدول محاولات الدخول المقيدة؛ لا يغير الترحيلات 001–003.
- `database/migrations/005_academic_management.sql`: يضيف صلاحية إسناد الأستاذ.
- `database/migrations/006_content_workflow.sql`: يضيف بيانات المصدر وقيود مراجعة المحتوى والنشر.
- `database/migrations/007_quizzes_and_attempts.sql`: يضيف مهل المحاولات وحقول التصحيح اليدوي ومحفزات تحقق الأسئلة والإجابات.
- `database/migrations/008_sessions_messaging.sql`: يتيح مصدر التسجيل المحلي أو مرجع المزود، إخفاء الرسائل لكل مشارك، وفهرسة المعدل؛ ويتحقق من إسناد الأستاذ للحصة.
- `database/migrations/009_subscription_management.sql`: يضيف فهرسًا لطابور انتهاء الاشتراكات النشطة.
- `database/migrate.php`: ينفذ ملفات الترحيل تحت PostgreSQL advisory lock، ويتحقق من SHA-256 للترحيلات المسجلة، ويطبق كل ملف داخل معاملة.
- `database/backup.php` و`database/restore.php`: إنشاء نسخة `pg_dump` خاصة مسجلة في `backup_records` والتحقق من بصمتها قبل الاستعادة المؤكدة إلى قاعدة الهدف.
- `GET /health`: فحص اتصال قاعدة البيانات باستجابة عامة لا تكشف الأسرار أو تفاصيل الاستثناء.
- لكل تغيير لاحق، أنشئ ملف ترحيل جديدًا برقم متزايد. لا تعدل ملف ترحيل طُبق على بيئة مشتركة.

الجداول تستخدم مفاتيح أجنبية وقيود تحقق وفهارس على مفاتيح البحث والربط. يستخدم سجل مراجعة المحتوى هدفًا واحدًا من المورد أو الامتحان أو السؤال؛ ويمنع القيد تسجيل هدفين في المراجعة ذاتها. الملفات تخزن بمفتاح تخزين خاص لا بمسار عام. ملفات الفيديو يمكن أن ترتبط بنسخ متعددة في `resource_variants`، وتخزن أحجامها بالبايت وبيانات الدقة ومعدل البت عند توفرها.

### بيانات أولية وقرارات البيانات

الترحيلات تزرع الأدوار والصلاحيات فقط. تحذف الترحيلة 006 صفوف البذور التجريبية من 003 إذا لم تكن مستخدمة، ثم يدخل المالك المراحل والصفوف والمواد يدويًا. لا تزرع موادًا أو أسعارًا. لا توجد بيانات طلاب حقيقية ضمن المستودع. لا ترفع PostgreSQL dump أو قاعدة محلية إلى GitHub.

## 7. تنفيذ التطبيق الحالي

### مكوّنات منفذة في المستودع

وجود المكوّنات التالية لا يعني أن خدمة خارجية اختيرت أو أن اختبارات تكاملها اجتازت CI.

- `app/Support/env.php`: تحميل إعدادات `.env` دون اعتماد خارجي.
- `app/Database/connection.php`: PDO PostgreSQL مع الاستعلامات الأصلية المحضرة ووضع أخطاء الاستثناء.
- `app/Auth/auth.php`: تسجيل طالب مع معاملة تشمل المستخدم والدور وملف الطالب؛ تسجيل الدخول، تجزئة/التحقق من كلمة المرور، تحديد المحاولات، التدقيق، تدوير الجلسة والخروج.
- `app/Security/authorization.php`: إعادة التحقق من الحساب النشط والأدوار لكل طلب، وفحص الصلاحيات من `role_permissions` ورفض API 403.
- `app/Security/audit.php`: `audit_log()` لكتابة الأحداث في `audit_events`.
- `app/Security/login_throttle.php`: قفل محاولات الدخول بإعدادات مطلوبة من `.env` وبصمة HMAC للبريد.
- `app/Services/AccountService.php`: إنشاء وتعديل وتعطيل الحسابات وتعيين الأدوار ومنع تعطيل آخر مدير نشط.
- `app/Services/AcademicService.php` و`app/Http/Controllers/AcademicController.php`: إدارة المراحل والصفوف والمواد وروابطها والدروس وإسناد الأساتذة، وتصفية الموارد حسب التصنيفات.
- `app/Http/Router.php` و`app/Http/Controllers/`: موجّه API ومتحكمات المصادقة والحسابات.
- `docs/OPEN_DECISIONS.md`: سجل القرارات المعلقة وقيم إعداد الأمان التي لا يجوز تخمينها.
- `app/Database/catalog.php`: قراءة المواد والصفوف والمراحل والدروس المنشورة للاستعراض.
- `app/Database/academics.php` و`app/Views/academics.php`: إضافة المراحل والصفوف والمواد وربطها بالصف من صفحة محمية بصلاحية `academics.manage`، مع معاملات وسجل تدقيق.
- `app/Database/access.php` و`app/Views/content_access.php`: قائمة طلاب مقسمة إلى صفحات، ومنح/سحب أهلية المحتوى يدويًا من المدير أو المراجع، مع سجل تاريخي وسجل تدقيق.
- `app/Database/staff.php` و`app/Views/staff.php`: دعوات لمرة واحدة وصالحة 48 ساعة لتفعيل حسابات الفريق، مع تعطيل/إعادة تفعيل وسجل تدقيق. المدير ومراجع المحتوى يستطيعان إنشاء حسابات الأستاذ والمراجع والمدير. رابط الدعوة يُشارك يدويًا ولا يعتمد على بريد آلي.
- `app/Database/questions.php` و`app/Views/questions.php`: بنك أسئلة يدعم التصنيف بالمادة والدرس والنوع والصعوبة، وإنشاء الأسئلة وتعديل المسودات والأسئلة المعادة، وإرسالها للمراجعة؛ اعتماد المراجع/المدير وحده ينشر السؤال.
- `app/Database/quizzes.php` و`app/Views/quizzes.php` و`app/Views/quiz_attempt.php`: صفحات عرض وإدارة الاختبارات والمحاولات. عمليات الاختبار تستخدم خدمات `QuizService` للتحقق من سياسات الوقت والمحاولات والتصحيح. يتوقف بدء المحاولة إذا لم يضبط المشغل سياسات الاختبارات الإلزامية. يلزم اختبار جميع المسارات على PostgreSQL الفعلي.
- `app/Views/`: تخطيط عربي RTL وصفحات البداية والمواد والتسجيل والدخول.
- `public/index.php` و`public/router.php`: نقطة الدخول وموجّه خادم التطوير للـ API والويب مع تمرير الملفات الثابتة مباشرة.
- `public/assets/`: CSS وJavaScript والصور والخطوط العامة، مع شعار AL WARITH.
- `storage/private/` و`storage/backups/`: مساحتان خارج web root للملفات الخاصة ونسخ PostgreSQL اليدوية. النسخ تنفذ عبر `database/backup.php` والاستعادة عبر `database/restore.php`؛ لا توجد جدولة أو سياسة تشفير/احتفاظ معتمدة.
- `database/create_admin.php`: ينشئ حساب مدير أول من الطرفية التفاعلية دون كلمة مرور افتراضية.

### أضيف في المرحلة الثانية

- API لإدارة المراحل والصفوف والمواد وربطها والدروس، وتفعيل السجلات أو تعطيلها دون حذف بيانات مترابطة.
- إسناد الأستاذ النشط ذي دور `teacher` إلى ربط صف ومادة، وإتاحة قائمة إسنادات الأستاذ الحالي.
- بحث API بالمرحلة والصف والمادة والدرس والنص ضمن الموارد المعتمدة؛ لا يعيد مفاتيح التخزين أو روابط الملفات.
- الترحيل `005_academic_management.sql` يضيف صلاحية `teaching_assignments.manage` إلى المدير فقط. المرحلة المتوسطة بلا صفوف مزروعة؛ يدخل المدير الصفوف بعد اعتماد أسمائها (OD-19).
- لم تُعدل الترحيلات 001–004. لم تُعدل `app/Views/` أو `public/assets/`؛ عقد API موثق في `docs/API_CONTRACT.md` ومصفوفة التتبع في `docs/TRACEABILITY_PHASE_2.md`.

### ما نُفذ وما لم ينفذ

تغطي المراحل 3–7 رفع الملفات وتنزيلها وسير مراجعة المحتوى والاختبارات الأساسية والحصص والرسائل الفردية والاشتراكات اليدوية والنسخ والاستعادة اليدويين وفحص الصحة. تظل هذه الوظائف مشروطة بإعداد البيئة واختبار التكامل في PostgreSQL؛ وجود الملفات وحده لا يعني أن CI أو النشر نجح.

يوجد adapter لـCloudflare Stream، لكنه يحتاج أسرار الحساب وبثًا فعليًا للتحقق التشغيلي. لا توجد بوابة دفع أو لوحة إدارة اشتراكات ضمن مسار إطلاق النسخة الأولى. توليد الأسئلة بالذكاء الاصطناعي والألعاب وبوابة ولي الأمر مؤجلة أو خارج النطاق. جدولة النسخ، وتشفيرها، والاحتفاظ بها، وRPO/RTO، واختبارات الضغط وUAT غير معتمدة أو غير منفذة. سجل التدقيق يسجل أحداث النطاق المذكورة في خدماته؛ لا يدعي المشروع تسجيل كل حدث محتمل.

واجهة إنشاء الحساب العامة تنشئ دور الطالب فقط. لا توجد صفحة عامة تسمح باختيار دور أستاذ أو مدير. لا تنشئ حساب مدير افتراضيًا أو بكلمة مرور ثابتة. منح الوصول للمحتوى يجب أن يكون قرارًا يدويًا مسجلًا من المدير/المراجع المخول، لا نتيجة دفع آلي.

نقاط API الحالية تشمل الجلسة والمصادقة وإدارة الحسابات والهيكل الدراسي والبحث والمحتوى والأسئلة والاختبارات والحصص والتسجيلات والرسائل الفردية. تفاصيلها في `docs/API_CONTRACT.md`، والتغطية والاختبارات في `docs/TRACEABILITY_PHASE_*.md`.

## 8. تشغيل المطور

المتطلبات: PHP 8.4+ مع `pdo_pgsql`، PostgreSQL وعميل `psql`، وGit. خطوات إنشاء قاعدة محلية وتشغيلها في `README.md`:

1. إنشاء دور وقاعدة محليين في PostgreSQL.
2. نسخ `.env.example` إلى `.env` وإدخال كلمة مرور محلية وقيم الأمان المعتمدة؛ القيم الإلزامية بلا افتراضات في المثال.
3. تشغيل `php database/migrate.php`.
4. تشغيل `php database/create_admin.php` من طرفية تفاعلية لإنشاء المدير الأول.
5. تشغيل خادم PHP على `public/`.

يستخدم كل مطور قاعدة محلية مستقلة، بينما يشترك الفريق في ملفات ترحيل SQL. لا تشاركوا `.env` أو قاعدة بيانات مطورة بين أعضاء الفريق.

## 9. الأمن والخصوصية

- استخدم أقل صلاحية لازمة لمستخدم PostgreSQL، ولا تستخدم حساب `postgres` من التطبيق.
- استخدم PDO والمعاملات عند حفظ العمليات المرتبطة، واهرب المخرجات عبر `htmlspecialchars`.
- نماذج POST تستخدم CSRF. يجب أن تستمر حماية CSRF وفحص الصلاحية في أي نموذج أو endpoint جديد.
- API يتطلب CSRF لكل طلب مغير، ويعيد تحميل حالة الحساب والأدوار من PostgreSQL في كل طلب.
- كلمات المرور مجزأة عبر PHP. لا تسجل كلمات المرور أو رموز الجلسات أو بيانات الدفع.
- السياسة الموحدة الحالية: 12 محرفًا على الأقل و72 بايت كحد أقصى. إعدادات مهلة الجلسة ومحاولات الدخول إلزامية بلا قيم افتراضية حتى يعتمدها مالك البيئة.
- يرسل التطبيق HSTS في الإنتاج (`APP_ENV=production`)؛ فعّل `SESSION_SECURE=1` خلف HTTPS.
- التطبيق يحتاج HTTPS في الإنتاج، و`SESSION_SECURE=1`، وحدود جلسات مناسبة.
- لا تخدم الملفات الخاصة من `public/`. نقاط التنزيل الحالية تتحقق من هوية المستخدم والصلاحية ومنحة الوصول اليدوية وحالة النشر قبل إرسال الملف.
- بيانات الطلاب قد تخص قُصّرًا؛ يجب تحديد الموافقات والاحتفاظ والحذف والإجراءات النظامية قبل الإطلاق.
- النسخ الاحتياطي والاستعادة اليدويان منفذان؛ الجدولة والتشفير وسياسة الاحتفاظ وتجربة الاستعادة في بيئة النشر تحتاج اعتمادًا وتشغيلًا موثقًا.
- لا تستخدم بيانات تجريبية أو شخصية حقيقية في مستودع Git.

## 10. قرارات لا تزال مطلوبة

- عدد الطلاب المتزامنين، عدد الحصص المتزامنة ومتوسط مدتها ونمو الاستخدام بعد سنة.
- تحديد زمن استجابة تقني وتوافر وRPO/RTO بمقاييس منفصلة.
- حدود خطة Cloudflare Stream وتكلفتها والجودة وسياسة الاحتفاظ بالتسجيلات.
- متوسط/حد حجم الفيديو وجوداته والتنزيل والاستئناف عند الانقطاع.
- ضبط واختبار مصفوفة الصلاحيات: المدير ومراجع المحتوى ينشئان حسابات الفريق ويعتمدان نشر الكتب والأسئلة والاختبارات.
- سياسة حقوق المحتوى وترخيص الكتب والملفات والتسجيلات.
- مدد الاحتفاظ بالرسائل والتسجيلات والبيانات والنسخ، والتشفير واختبارات الاستعادة.
- سياسة إدارة الحسابات وكلمات المرور والمصادقة متعددة العوامل وقفل محاولات الدخول.
- قواعد الاختبار: مدة ومحاولات افتراضية، سياسة المحاولة غير المكتملة، عرض النتائج، ونافذة الاختبار في الواجهة.
- تسليم سياسة الخصوصية والاستخدام، بما فيها الطلاب القُصّر وإجراءات الموافقة والحذف.
- مزود وتواتر ومدة الاحتفاظ بالنسخ الخارجية، والتشفير، وقيم RPO/RTO واختبار الاستعادة.
- شركة وخطة الاستضافة، موقع مركز البيانات، وأعداد المستخدمين المتزامنين المتوقعة.

لا تخترع قيمًا لهذه البنود؛ سجل القرار في Issue/وثيقة، ثم حدّث المخطط والتطبيق والوثائق عند اعتماده.

## 11. تقسيم العمل بين الفريقين

- **فريق الخلفية:** `app/`, `database/`, مصادقة PHP، PDO، الترحيلات، الصلاحيات، التكاملات والتشغيل.
- **فريق الواجهة:** `app/Views/`, `public/assets/`, تجربة RTL والتجاوب وسهولة الاستخدام.
- **مشترك:** عقد البيانات والـ API إن أضيف، تعديل مخطط يؤثر على صفحات، وحقوق الوصول وحالات الخطأ.

قبل مهمة مشتركة، اتفقوا على الحقول والمدخلات والمخرجات وحالات الخطأ والصلاحيات. لا تدفعوا مباشرة إلى الفرع الافتراضي؛ استخدموا فرعًا وPull Request وراجعوا تغييرات الترحيلات بعناية.

## 12. توجيهات للمساعد البرمجي

1. حافظ على PHP 8.4+ وPostgreSQL وPDO ما لم يصدر قرار جديد صريح.
2. اقرأ الترحيلات والشيفرة الفعلية قبل تعديلها، وميّز المتطلب عن التنفيذ.
3. لا تعدل ترحيلًا سبق تطبيقه؛ أنشئ ترحيلًا جديدًا.
4. استخدم استعلامات PDO المحضرة ومعاملات مناسبة، واختبر حالات الصلاحية السلبية والإيجابية.
5. لا تخترع أسعارًا أو عملات أو بيانات مناهج أو موفري خدمات أو مدد احتفاظ.
6. لا تعرض ملفات أو تسجيلات خاصة برابط عام. تحقق من صلاحية المستخدم ومنحة الوصول اليدوية على الخادم.
7. حافظ على دعم العربية RTL والاتصال المحدود.
8. حدّث جميع ملفات Markdown عند تغير التقنية أو الحالة أو القرارات. لا تصف ميزة مخططة بأنها منفذة.

## 14. حالة المرحلة الثالثة: المحتوى والملفات

- رفع الكتب والموارد والامتحانات السابقة إلى `storage/private/` بمفتاح عشوائي وفحص MIME/الحجم. يجب تحديد `UPLOAD_MAX_BYTES` في بيئة التشغيل، ولا توجد قيمة افتراضية؛ راجع OD-14 وOD-21.
- حالة المحتوى ومسار المراجعة: `DRAFT → PENDING_REVIEW → APPROVED|REJECTED`. حقول المصدر والمالك والترخيص مطلوبة قبل الإرسال. سجل `content_reviews` وتحديث النشر يقعان ضمن معاملة واحدة، وتمنع قيود قاعدة البيانات النشر دون موافقة.
- الأستاذ لا يرفع أو يرسل إلا لمادة وصف مرتبط بها في `teaching_assignments`. المراجع لا يعتمد محتواه بنفسه.
- التنزيل عبر API محمي بالجلسة والصلاحية، وحالة النشر وسجل الموافقة ومنحة الوصول اليدوية للطالب. يدعم Range للملف الأساسي والنسخ البديلة القابلة للتنزيل، ولا يعرض مفتاح تخزين أو رابطًا عامًا.
- الموارد والأسئلة ترتبط بالصف والمادة ويمكن ربطها بدرس؛ الامتحانات السابقة ترتبط بالصف والمادة. كلها تخضع لمسار المسودة والمراجعة.
- وثائق العقد والتتبع: `docs/API_CONTRACT.md` و`docs/TRACEABILITY_PHASE_3.md`.
- الترحيل `006_content_workflow.sql` يضيف حقول مصدر للأسئلة والامتحانات والموارد، وقيود/محفزات انتقال الحالة والمراجعة. سكربت التراجع اليدوي هو `database/rollback/006_content_workflow.sql`. يوقف التطبيق قبل تشغيله، ولا ينفذ في بيئة مشتركة قبل مراجعة البيانات؛ فهو يحذف بيانات المصدر والطابع الزمني للنشر وسجلات مراجعة المرحلة.

## 15. حالة المرحلة الرابعة: الأسئلة والاختبارات

- تدار الأسئلة المعتمدة بمرشحات المرحلة والصف والمادة والدرس والنوع والصعوبة. MCQ يتطلب خيارين على الأقل وإجابة صحيحة واحدة، وصح/خطأ خيارين وإجابة صحيحة واحدة، والمقالي بلا خيارات؛ هذا يطابق مخطط الإجابة ذات الخيار المفرد.
- الاختبار مرتبط بمادة، ولا يضاف إليه إلا سؤال معتمد من المادة نفسها. الطالب لا يرى مفتاح الإجابة قبل النتيجة.
- يبدأ الطالب الاختبار ضمن نافذته، وتخزن لكل محاولة مهلة نهائية على الخادم. الحفظ والإرسال يعيدان فحص الملكية وحالة المحاولة والوقت وعدد المحاولات ومنحة الوصول اليدوية.
- التصحيح الموضوعي آلي على الخادم. الإجابات المقالية تنتظر تصحيح الأستاذ المسند للمادة. الطالب يرى محاولته وحدها؛ الأستاذ يرى محاولات مواده المسندة.
- `QUIZ_MAX_ATTEMPTS`, `QUIZ_DURATION_MINUTES`, `QUIZ_RESULT_VISIBILITY`, `QUIZ_INCOMPLETE_ATTEMPT_POLICY` إلزامية عند تشغيل المسارات ذات الصلة، وبلا قيم افتراضية. خياراتها موثقة في `docs/API_CONTRACT.md`، والقراران OD-20 وOD-22 معلقان لحين اعتماد المالك.
- الترحيل `007_quizzes_and_attempts.sql` يضيف المهلة وحقول التصحيح اليدوي ومحفزات حماية الأسئلة والإجابات. التراجع اليدوي في `database/rollback/007_quizzes_and_attempts.sql` يحذف البيانات المضافة للمهل والتصحيح اليدوي؛ أوقف التطبيق وخذ نسخة وراجع البيانات قبل استخدامه.
- مصفوفة التتبع في `docs/TRACEABILITY_PHASE_4.md`.

## 16. حالة المرحلة الخامسة: الحصص والرسائل

- الأستاذ يدير مواعيد حصص مواده المسندة؛ الأدمن يستطيع اختيار أستاذ مسند. التطبيق وقاعدة البيانات يتحققان من الإسناد.
- مسار الانضمام يتحقق من المستخدم والصف وحالة الحصة والنافذة الزمنية، ومن منحة الوصول اليدوية للطالب. لا يعاد رابط البث في قوائم الحصص أو عند إنشائها وتحريرها، وإنما يصدر موقّعًا عند الانضمام.
- `app/Services/LiveMeetingProvider.php` يربط Cloudflare Stream Live Inputs مع التسجيل الآلي وروابط المشاهدة الموقعة. بيانات RTMPS تظهر مرة واحدة ولا تحفظها المنصة. يحتاج الربط اختبارًا ببيانات الحساب وبث فعلي.
- التسجيلات الخاصة متاحة بعد نهاية الحصة وبعد `available_from`، ويجب أن تكون `READY`. المصدر ملف في التخزين الخاص أو Cloudflare Stream. الطالب يحتاج منحة وصول يدوية نشطة؛ لا توجد روابط عامة.
- الرسائل فردية فقط بين طالب وأستاذ له إسناد لمادة في صف الطالب. توجد حالة قراءة وحذف منطقي منفصل لكل طرف. الحد `MESSAGING_RATE_LIMIT_COUNT` والنافذة `MESSAGING_RATE_LIMIT_WINDOW_SECONDS` إلزاميان للإرسال وبلا قيمة افتراضية؛ OD-23 معلق.
- الترحيل الجديد `008_sessions_messaging.sql` يجعل `session_recordings.storage_key` اختياريًا مع شرط مصدر، ويضيف حقول الحذف لكل مشارك. التراجع اليدوي في `database/rollback/008_sessions_messaging.sql` يتعذر إذا وجدت تسجيلات مصدرها مزود بلا ملف.
- عقد المسارات والأخطاء في `docs/API_CONTRACT.md` ومصفوفة التتبع في `docs/TRACEABILITY_PHASE_5.md`.

## 17. حالة المرحلة السادسة: الاشتراكات

- يستطيع المدير إنشاء الخطط وتعديلها وتفعيلها أو تعطيلها، وإسناد اشتراك يدويًا للطالب، ومراجعة سجلات الاشتراك وتحديث حالتها وفترتها. لا توجد بوابة دفع أو عملية دفع آلية.
- السعر والعملة في الخطة اختياريان ولا توجد قيمة افتراضية. إذا سجّل المدير سعرًا، يجب أن يسجل العملة معه. إنشاء اشتراك يدوي يتطلب إدخال المبلغ والعملة والحالة وتاريخ البداية؛ تاريخ النهاية إما يدخل صراحة أو يحسب من مدة الخطة التي اختارها المدير.
- `has_manual_content_access(user_id)` هو الفحص الموحد لأهلية المحتوى والاختبارات والحصص والتسجيلات في الإطلاق. جداول الاشتراكات موجودة للتوسع لكنها لا تمنح هذه الأهلية.
- تُعالج الانتهاءات عند فحص اشتراك الطالب، ويمكن تشغيل دفعة لجميع الاشتراكات عبر `POST /api/v1/admin/subscriptions/expire` أو الأمر `php database/expire_subscriptions.php` لجدولة تشغيله من بيئة الاستضافة.
- لا توجد أسعار أو بوابة دفع ضمن إطلاق النسخة الأولى؛ التفاصيل المستقبلية موثقة في عقد API ومصفوفة `docs/TRACEABILITY_PHASE_6.md`.
- ترحيل `009_subscription_management.sql` يضيف فهرس انتهاء جزئيًا فقط. التراجع `database/rollback/009_subscription_management.sql` يحذف الفهرس، ولا يحذف بيانات الخطط أو الاشتراكات.

## 18. حالة المرحلة الثامنة: الاختبارات والتتبع

- `.github/workflows/backend-ci.yml` يهيئ PHP 8.4 وPostgreSQL 16، يطبق الترحيلات، ويشغل فحوصات syntax والوحدة والفحوصات الساكنة وتكاملي الحسابات والدراسة وHTTP والنسخ والاستعادة.

- الوصف العام في `README.md` يميز الوظائف الموجودة في المستودع عن نتائج الاختبار والوظائف المؤجلة؛ نتيجة workflow لا تُسجل نجاحًا قبل تشغيله.
