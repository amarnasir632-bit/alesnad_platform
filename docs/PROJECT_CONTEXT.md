# سياق المشروع للفرق والمساعدات البرمجية

> اقرأ هذا الملف قبل اقتراح تغييرات أو تنفيذها. يشرح هذا الملف غرض المشروع ومتطلباته المعتمدة في المسودات الحالية، ثم يميزها بوضوح عن حالة الكود الموجودة. لا تعتبر المتطلب منفذًا لمجرد وروده هنا أو في BRD/SRS.

## 1. تعريف المشروع

**اسم المشروع:** منصة الإسناد الأكاديمي. تستخدم مسودتا BRD وSRS الاسم الوصفي «منصة تعليمية رقمية».

**الشركة المشرفة/المنفذة:** AL WARITH (الوارث)، وفق إفادة مالك المشروع. الشعار المعتمد المرفق محفوظ في `assets/brand/al-warith-logo.jpg`.

**الاسم التجاري:** «منصة الإسناد الأكاديمي»؛ صححنا كتابة «الأكادمي» إلى «الأكاديمي» إملائيًا مع الحفاظ على الاسم المقصود.

**نوع النظام:** منصة ويب تعليمية عربية تجمع المحتوى والتقييم والتعلم المباشر والمسجل والتواصل بين الطالب والمعلم.

**السياق الجغرافي والتعليمي:** السودان والمنهج السوداني، وفق قرار OD-01 في BRD. يجب اعتماد أسماء المراحل والصفوف والمواد والمحتوى النهائي من مالك المشروع قبل تعبئتها في النظام.

**المستخدمون الرئيسيون:** الطالب، المعلم، مدير المنصة، ومشرف المحتوى/الامتحانات. ولي الأمر فئة محتملة مشروطة وليست ضمن الإطلاق حتى يعتمد نطاقها وصلاحياتها.

**القيمة الأساسية:** نقطة وصول منظمة وآمنة للكتب والدروس والامتحانات والتقييم والتواصل، تعمل قدر الإمكان مع اتصال إنترنت محدود أو غير مستقر وتدعم التوسع إلى صفوف ومراحل أخرى.

## 2. قاعدة قراءة المعلومات وحالة الحقيقة

هذا الملف يلخص BRD وSRS ومخطط قاعدة البيانات والكود المفحوص في المستودع. عند التعارض:

1. متطلبات العمل المعتمدة وقرارات مالك المشروع تحدد ما ينبغي أن يفعله المنتج.
2. SRS يشرح سلوك النظام المطلوب وطرق التحقق، لكنه مسودة أولية، وليس دليلًا على وجود تنفيذ.
3. الكود ونماذج البيانات والترحيلات هي الدليل على ما ينفذه المستودع حاليًا.
4. مخطط `SqlDigram/` تصور ERD أولي، ولا يمثل مخطط قاعدة البيانات الفعلي في Django.
5. أي سؤال أو رقم أو سياسة موسومة «مفتوح»، «مطلوب من العميل»، «لاحق» أو «مشروط» يظل غير محسوم. لا تخترع إجابة نيابة عن مالك المشروع.

**تمييز مهم:** وصف المشروع ومتطلباته يحدد PHP 8.4+ وPostgreSQL وPDO ضمن التقنية المستهدفة. أما الكود الحالي في هذا المستودع فهو Python/Django ويستخدم SQLite. لذلك يوجد عدم توافق جوهري بين التقنية المستهدفة والتنفيذ الحالي. لا توسع هذا التنفيذ على أنه مطابق للتقنية المعتمدة، ولا تبدأ ترحيلًا بين التقنيتين من تلقاء نفسك؛ ارفع التعارض للفريق ليقرر إن كان المستودع نموذجًا أوليًا مؤقتًا أم أن اختيار التقنية قد تغير رسميًا.

## 3. التقنيات والمعمارية المستهدفة

### التقنيات المعتمدة في وصف المشروع

| الطبقة | التقنية | الاستخدام |
| --- | --- | --- |
| الواجهة | HTML5 | بنية الصفحات |
| الواجهة | CSS3 | التنسيق والتجاوب ودعم RTL |
| الواجهة | JavaScript ES6+ | التفاعلات في المتصفح |
| الخادم | PHP 8.4 أو أحدث متوافق | منطق الأعمال ومعالجة الطلبات والمصادقة والصلاحيات |
| قاعدة البيانات | PostgreSQL | تخزين البيانات المستمر |
| اتصال البيانات | PDO وSQL محضّر | وصول آمن إلى البيانات والاستعلامات |
| تبادل البيانات | JSON عند الحاجة إلى API | طلبات واستجابات الخدمات |
| الإصدارات والتوثيق | Git وMarkdown | التعاون وتوثيق المشروع |

المعمارية المطلوبة عميل/خادم: الواجهة تعرض البيانات وتتفاعل مع المستخدم؛ الخادم ينفذ منطق الأعمال ويتحقق من المدخلات والصلاحيات؛ PostgreSQL تخزن البيانات. كل تحقق أمني أو قرار صلاحية يجب تنفيذه على الخادم، ولا يعتمد على JavaScript وحده. لا يفرض وصف المشروع إطار عمل PHP في هذه المرحلة.

### ما يستخدمه المستودع فعليًا حاليًا

- Python، مع `Django==6.1.2` في `requirements.txt`، إضافة إلى `python-dotenv`.
- SQLite في `config/settings.py` وقاعدة محلية `db.sqlite3`.
- قوالب Django وHTML، وCSS وJavaScript عاديان في `templates/` و`assets/`.
- لا توجد شيفرة PHP أو إعداد PostgreSQL أو PDO أو API JSON أو تكامل بث أو تخزين خارجي في الملفات المفحوصة.
- بيئة التنفيذ الحالية تعتمد جلسات Django ومستخدم Django الافتراضي؛ ليست نظام الأدوار المذكور في SRS.
- الإعدادات تقرأ `DJANGO_SECRET_KEY`, `DJANGO_DEBUG`, و`DJANGO_ALLOWED_HOSTS` من البيئة/`.env`؛ القيم الافتراضية مخصصة للتطوير (`DEBUG=True` ومفتاح محلي غير صالح للإنتاج). إعداد الإنتاج والأسرار ومضيفوه لم تُجهز.
- البريد مضبوط على `django.core.mail.backends.console.EmailBackend` للتطوير، لا على مزود بريد فعلي.

**تعليمات للمساعد البرمجي:** عند إجراء تغيير برمجي، افحص التقنية والملفات الفعلية أولًا، واذكر صراحة إن كان التغيير يستهدف النموذج الحالي أم التقنية المستهدفة. لا تعرض تقنية مستهدفة كأنها مستخدمة فعليًا، ولا تدّع اكتمال ميزة من المتطلبات دون كود أو اختبار يثبتها.

## 4. أهداف ونطاق المنتج

### أهداف الأعمال

- جمع مصادر التعلم في منصة واحدة بدل تشتتها بين ملفات وقنوات متعددة.
- تصنيف المحتوى حسب المرحلة والصف والمادة والوحدة/الدرس.
- تمكين الطالب من الدراسة الذاتية، مراجعة التسجيلات، وإجراء تقييمات.
- تمكين المعلمين والمسؤولين المخولين من إعداد المحتوى والأسئلة والحصص ومراجعتها.
- تقليل أثر ضعف الإنترنت عبر ملفات قابلة للتنزيل حيث تسمح الحقوق، وموارد خفيفة وسلوك مناسب عند الانقطاع.
- بناء تنظيم بيانات وصلاحيات يسمح بإضافة مراحل وصفوف وخدمات مستقبلًا.

### المرحلة الأولى حسب BRD/SRS

- الحسابات وتسجيل الدخول وإدارة الأدوار والصلاحيات.
- إدارة المراحل والصفوف والمواد والدروس.
- مكتبة ملفات تعليمية مع البحث والتنزيل المقيد بالصلاحيات وحقوق النشر.
- بنك أسئلة مصنف حسب الصف والمادة والدرس والنوع والصعوبة.
- أرشيف امتحانات سابقة قابل للبحث والتصفية والعرض والتنزيل.
- وصول المحتوى المدفوع وفق اشتراك شهري؛ طريقة التحصيل/بوابة الدفع لم تُحدد بعد.
- اختبارات إلكترونية أساسية وتصحيح آلي للأنواع القابلة لذلك، وعرض النتائج حسب سياسة التقييم.
- إدارة مراجعة المحتوى واعتماده وحالة النشر.
- جدولة الحصص وربطها بمزود بث خارجي وإتاحة التسجيلات عند توفرها وبعد التحقق من الصلاحيات. المعلن مبدئيًا خمس حصص مباشرة في الأسبوع، وبقية الحصص/المحتوى تكون مسجلة.
- رسائل بين الطالب والمعلم مع سياسة استخدام واحتفاظ وإشراف معتمدة.
- لوحة إدارة للمستخدمين والمحتوى والمواد والامتحانات.
- واجهة عربية RTL ومتجاوبة للهواتف والحواسيب.
- أمان ونسخ احتياطي ومراقبة أساسية.

### لاحق أو مشروط

- توليد أسئلة وإجابات بالذكاء الاصطناعي من محتوى معتمد؛ مراجعة بشرية قبل النشر، وشفافية للمراجع، وسياسة خصوصية وتكلفة لمزود الخدمة.
- لعبة تعليمية بمراحل ونقاط ومحاولات وتغذية راجعة، دون نسخ علامات أو تصميمات محمية.
- بوابة ولي الأمر، تطبيق هاتف مستقل، تقارير متقدمة، شهادات، وإشعارات موسعة تحتاج اعتماد نطاق مستقل. الاشتراك الشهري أصبح قرارًا معتمدًا من مالك المشروع، لكن تفاصيل الدفع الإلكتروني والتسعير والتجديد لم تحسم.
- إضافة صفوف ومراحل ومناهج جديدة ضمن خطة التوسع.

### خارج النطاق الحالي ما لم يعتمد لاحقًا

- تصوير وإنتاج كامل المحتوى من الصفر.
- تشغيل الرسائل أو البث المباشر دون إنترنت.
- ضمان سعة غير محدودة أو سرعة مطلقة دون تحديد ميزانيات ومقاييس واختبارات.
- تصحيح آلي كامل للأسئلة المقالية دون مراجعة وضوابط جودة.
- الدفع الإلكتروني قبل تحديد الدولة والعملة والمزود والالتزامات.

## 5. الأدوار ورحلات الاستخدام

### الطالب

يسجل الدخول، يختار المرحلة والصف والمادة، يصل إلى درس أو كتاب أو امتحان مسموح، ينضم إلى حصة أو يشاهد تسجيلًا متاحًا، يؤدي اختبارًا ويرى نتيجته حسب السياسة، ويراسل المعلم المخول.

### المعلم

يدير المواد والحصص المسندة إليه، ينشئ أو يرفع المحتوى والأسئلة والامتحانات، يحفظ المسودة أو يرسلها للمراجعة، يجدول الحصة ويربطها بمزود البث، ويتابع النتائج ويرد على الرسائل. محتوى الذكاء الاصطناعي، إن اعتمد، يحتاج مراجعة المعلم قبل نشره.

### مدير المنصة

يدير الحسابات والأدوار والمراحل والصفوف والمواد والمحتوى والسياسات العامة.

### مشرف المحتوى/الامتحانات

يصنف الكتب والامتحانات والأسئلة، يتحقق من الحقوق والجودة، ويعتمد أو يرفض النشر بحسب الصلاحيات.

### ولي الأمر

قد يتابع التقدم أو النتائج إذا اعتمدت الفئة لاحقًا. لا تفترض صلاحية الوصول إلى بيانات الطالب دون قرار صريح وسياسة خصوصية.

## 6. قواعد العمل والأمان

- المحتوى مرتبط بالتصنيفات الدراسية الصحيحة وبحالة النشر والترخيص، ولا يصل إليه إلا المستخدم المصرح له.
- الأدوار المذكورة في SRS هي الطالب والمعلم ومدير المنصة ومشرف المحتوى. يجب التحقق من الصلاحية عند كل طلب محمي على الخادم، بما في ذلك تنزيل الملفات والروابط المباشرة.
- كلمات المرور لا تخزن بنص صريح؛ تستخدم آلية تجزئة آمنة يوفرها إطار الخادم المعتمد.
- الأسئلة والمحتوى المولد آليًا لا ينشر تلقائيًا قبل اعتماد بشري، إذا نُفذت ميزة الذكاء الاصطناعي.
- تُحفظ نتائج الاختبار مع الطالب والاختبار والمحاولة اللازمة لإثبات النتيجة. سياسة الانقطاع والمحاولات والوقت والتصحيح تحتاج تحديدًا.
- حقوق الملفات والتسجيلات ومصدرها ومالكها وترخيصها وموافقة النشر يجب تسجيلها حيث يلزم.
- يجب تحديد سياسة الاحتفاظ والحذف للرسائل والتسجيلات وبيانات الطلاب والسجلات التشغيلية، مع مراعاة القُصّر إن انطبق ذلك.
- لا تضع مفاتيح الخدمات أو الأسرار في المستودع؛ استخدم إعدادات البيئة، ولا تكشفها في السجلات أو رسائل الخطأ.
- اتصالات البث والتخزين والذكاء الاصطناعي خدمات خارجية؛ وثق حدود الاعتماد وسلوك الفشل بعد اختيار المزود.

## 7. المتطلبات غير الوظيفية

- **الاتصال المحدود:** تقليل حجم الموارد والطلبات، ضغط الملفات/الصور، إتاحة التنزيل المصرح به، وتحديد سلوك الاستئناف والتخزين المؤقت وجودة الفيديو. لا يوجد قياس رقمي معتمد حتى الآن.
- **الأداء والسعة:** تحديد أزمنة الاستجابة وحجم الطلبات والمستخدمين المتزامنين والحصص المتزامنة قبل اختبار الضغط.
- **التوافر والاستعادة:** اعتماد نسبة التوافر وRPO وRTO وتواتر النسخ الاحتياطي وإجراءات اختبار الاستعادة.
- **التوافق:** اعتماد الأجهزة والمتصفحات ومعايير الوصول والواجهة العربية قبل القبول النهائي.
- **الخصوصية:** تقييد بيانات الطلاب والرسائل والنتائج، وتحديد الموافقات والاحتفاظ والحذف.
- **التشغيل والمراقبة:** مراقبة الأخطاء والاستهلاك والعمليات المهمة، وتحديد التنبيهات والمسؤول عنها.
- **الاعتمادية الخارجية:** التعامل برسائل واضحة عند تعطل البث أو التخزين، وتسجيل الخطأ دون تسريب أسرار.

لا توجد في المسودات قيم رقمية نهائية للأداء أو السعة أو التوافر أو الاحتفاظ. لا تحول صفات مثل «سريع» و«قليل البيانات» إلى أرقام من عندك.

## 8. معايير قبول المستوى العالي

1. اعتماد نطاق المرحلة الأولى والصفوف والمواد.
2. وصول الطالب للمحتوى المصرح فقط ورفض الوصول المباشر غير المصرح.
3. تمكين المسؤول المخول من إضافة المحتوى وتصنيفه ومراجعته ونشره.
4. تنفيذ اختبار أساسي وعرض نتيجته وفق قواعد متفق عليها.
5. نجاح تكامل البث والتسجيل والمشاهدة اللاحقة عند اختيار المزود.
6. نجاح المراسلة بين طالب ومعلم مخولين.
7. تنفيذ اختبارات الأمان والأداء بالأرقام المتفق عليها.
8. توثيق النسخ الاحتياطي والاستعادة ومسؤوليات الدعم وإدارة المحتوى.
9. معالجة العيوب الحرجة قبل قبول المرحلة.

هذه معايير وثائقية مستهدفة؛ لا يعني ذكرها أن النظام يحققها الآن.

## 9. حالة التنفيذ الموجودة في المستودع

المستودع الحالي تطبيق Django أولي محدود، وليس تنفيذًا كاملًا لـ BRD/SRS.

| الجزء | ما يفعله الكود الحالي | ما لا يثبت وجوده حاليًا |
| --- | --- | --- |
| الصفحة الرئيسية | تعرض حتى 3 دورات منشورة | لوحة تعلم أو متابعة تقدم |
| الحسابات | تسجيل حساب عبر Django User وتسجيل الدخول والخروج | أدوار طالب/معلم/مشرف مخصصة أو إدارة صلاحيات مفصلة |
| الدورات | قائمة وتفاصيل للدورات المنشورة | تصنيف هرمي حسب المرحلة/الصف/المادة/الوحدة |
| التسجيل | المستخدم المسجل يستطيع الانضمام للدورة؛ يوجد قيد فريد لكل طالب ودورة | قيود صلاحية/اشتراك مدفوع أو محتوى تعليمي مرتبط بالدورة |
| الدروس | مرتبطة بالدورة، لها محتوى نصي ورابط فيديو اختياري | إدارة بث حي أو تسجيلات أو تخزين محمي |
| الاختبارات والأسئلة | لا توجد نماذج تنفيذية لها في Django | بنك أسئلة، محاولات، إجابات، نتائج أو تصحيح آلي |
| التواصل | لا توجد نماذج أو شاشات رسائل | محادثات، إشراف أو سياسة احتفاظ |
| الإدارة | تطبيق Django admin مسجل للدورات والدروس والتسجيلات | لوحة عمل كاملة للأدوار والعمليات المذكورة في SRS |
| قاعدة البيانات | SQLite في الإعدادات المحلية | PostgreSQL أو إعداد إنتاج |
| التكاملات | لا يظهر تكامل خدمات خارجية | بث، تخزين ملفات خارجي، بريد فعلي أو ذكاء اصطناعي |

### نماذج Django الموجودة

- `Course`: عنوان، ملخص، وصف، اسم المعلم كنص، حالة نشر، تاريخ إنشاء.
- `Lesson`: دورة، عنوان، محتوى نصي، رابط فيديو اختياري، ترتيب.
- `Enrollment`: مستخدم Django ودورة وتاريخ تسجيل؛ قيد فريد على الزوج `(student, course)`.
- تسجيل المستخدم يستخدم `django.contrib.auth.models.User`؛ نموذج التسجيل يجمع اسم المستخدم والبريد وكلمة المرور من خلال `UserCreationForm`.

### الصفحات والمسارات الحالية

- `/` الصفحة الرئيسية (`core:home`).
- `/accounts/register/` إنشاء حساب.
- `/accounts/login/` و`/accounts/logout/` عبر عروض Django المدمجة.
- `/courses/` قائمة الدورات المنشورة.
- `/courses/<id>/` تفاصيل دورة منشورة.
- `/courses/<id>/enroll/` تسجيل في الدورة بطلب POST مع تسجيل دخول.
- `/admin/` إدارة Django المدمجة.

### بنية الملفات التي تهم الفريقين

- `config/`: إعدادات Django والمسارات وASGI/WSGI.
- `accounts/`: نموذج التسجيل وعرضه ومسارات الحساب.
- `courses/`: النماذج والعروض والمسارات ولوحة admin والترحيلات.
- `core/`: الصفحة الرئيسية.
- `templates/base.html` و`*/templates/`: القوالب وواجهة Django الحالية.
- `assets/css/style.css`, `assets/js/main.js`, الصور والخطوط: أسلوب وسلوك الواجهة.
- `index.html`: صفحة HTML مستقلة؛ تحقق من دورها الحالي قبل اعتبارها جزءًا من رحلة Django.

## 10. ERD والمستندات مقابل الكود

المخطط الأولي يسمي كيانات مثل: `User`, `Role`, `Permissions`, `UserRole`, `PermissionsRole`, `Employees`, `students`, `Stages`, `Classes`, `Subject`, `ClassSubject`, `Resource`, `Questions`, `QuestionOptions`, `PastExams`, `Quizzes`, `QuizQuestions`, `QuizAttempts`, `StudentAnswers`, `LiveSessions`, `Messages`, `ContentReviews`, `Subscriptions`.

أما جدول الكيانات المقترح في SRS فيشمل مفاهيم `User/Role`, `Stage/Grade/Subject`, `Lesson/LearningResource`, `Question/QuestionOption`, `PastExam`, `Quiz/Attempt/Result`, `LiveSession/Recording`, `Message`, `ContentReview`, `AuditEvent/BackupMetadata`.

هذه نماذج مقترحة تحتاج مراجعة وتوحيدًا قبل التنفيذ. لا تنشئ جداول Django على أساس أسماء المخطط وحدها. يوجد اختلاف اصطلاحي بين ERD وSRS، كما أن `Course`, `Lesson`, `Enrollment` الحالية لا تغطي كل ذلك. خطط لمراجعة ERD مع متطلبات الصلاحيات والتصنيفات والحقوق وحالات النشر قبل بناء قاعدة الإنتاج.

## 11. تقسيم الفريق والعمل المشترك

المشروع مستودع واحد وفريقان؛ لا تفصل الواجهة والخلفية في مستودعين دون قرار معماري.

- **فريق الخلفية:** منطق الخادم، الحسابات والصلاحيات، النماذج والترحيلات، المسارات/واجهات API، قواعد البيانات، التكاملات، الأمن والتشغيل.
- **فريق الواجهة:** القوالب أو صفحات الويب، HTML/CSS/JavaScript، التجاوب، RTL وإتاحة الوصول.
- **مشترك:** عقود البيانات والواجهات، تغييرات القوالب التي تعتمد على بيانات الخادم، حالات النشر والتصنيف، الترحيلات التي تؤثر على العرض، وتوثيق تجربة المستخدم.

قبل تطوير ميزة عابرة للفريقين، اتفقوا على شكل البيانات والمدخلات/المخرجات وحالات الخطأ والصلاحيات. احتفظوا بهذا العقد في Issue أو وصف Pull Request، واطلبوا مراجعة الطرف المتأثر. مجلدات `templates/` و`assets/` متاحة حاليًا ضمن كود Django؛ حدود المسؤولية تنظيمية وليست صلاحيات GitHub تلقائية.

## 13. إرشادات للمساعدات البرمجية

1. ابدأ بقراءة هذا الملف والملفات التي ستعدلها؛ الكود قد يتغير بعد تاريخ إعداد هذا السياق.
2. ميّز في الإجابة بين **المتطلب** و**التنفيذ الحالي** و**اقتراح جديد**.
3. لا تنشئ أو تدّع أدوارًا أو جداول أو مسارات أو تكاملات غير موجودة دون تنفيذها.
4. إذا طُلبت ميزة، تحقق أولًا من توافقها مع التقنية المختارة. عند التعارض بين PHP/PostgreSQL المستهدفة وDjango/SQLite الحالية، وضح أثر القرار قبل تغييرات معمارية واسعة.
5. احمِ بيانات الطلاب والمحتوى: صلاحية على الخادم، تحقق من المدخلات، كلمات مرور مجزأة، استعلامات محضّرة/ORM، أسرار في البيئة، وتنزيل ملفات مصرح به.
6. لا تخترع أرقام أداء أو سياسة أو موردًا خارجيًا. اترك القرارات المفتوحة معلّمة أو اطلب اعتمادها عند الحاجة.
7. احفظ واجهة عربية RTL ومتجاوبة، وراع الاتصال المحدود عند بناء الواجهة والوسائط.
8. عند تنفيذ التغيير، حدّث الوثائق ذات الصلة ووضح ما أصبح مطبقًا وما بقي خارج النطاق.
