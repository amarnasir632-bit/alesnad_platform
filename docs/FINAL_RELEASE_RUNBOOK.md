# دليل الإكمال اليدوي والإطلاق

نفّذ المراحل بالترتيب. لا تتجاوز بوابة توقف فاشلة ولا تضع أسرارًا في Git أو ترسلها في المحادثات. ارفع الموقع للعامة فقط بعد اجتياز بوابة الإطلاق الأخيرة. هذه الخطة لا تختار قيمًا تشغيلية أو تجارية بدل مالك المنصة.

## ما تحتاج تجهيزه

- صلاحية مستودع GitHub لقراءة الـworkflow ومتابعة نتيجته، وصلاحية دمج التغيير بعد مراجعته.
- عنوان خادم الاستضافة ونظامه، صلاحية SSH، نطاق تملكه، وشهادة TLS للأصل.
- حساب Cloudflare للنطاق وCloudflare Stream، وقدرة إنشاء API Token بصلاحيات Stream المناسبة.
- وجهة نسخ احتياطي خارج خادم التطبيق، وحساب تخزين تتحكم بصلاحياته.
- مالك قرارات المنتج والتشغيل لحسم القيم في «ورقة القرارات» أدناه.
- حسابات ممثلين للاختبار: مدير، مراجع محتوى، أستاذ، طالب، وطالب بلا وصول.

## المرحلة 1: ثبّت نطاق الإصدار والقرارات

اقرأ `docs/OPEN_DECISIONS.md` وراجع كل قرار في الجدول التالي مع صاحب الصلاحية. اكتب الإجابات في سجل تشغيل خاص، ثم حدّث ملف القرارات بالمستودع بعد اعتمادها. لا تخمّن أرقامًا ولا تنسخ قيم CI إلى الإنتاج.

| القرار | المطلوب اعتماده قبل الإعداد | أثره |
| --- | --- | --- |
| نطاق SRS | أكد أن بوابة ولي الأمر واللعبة وتوليد AI وتطبيق الهاتف مؤجلة أو اكتب أنها مطلوبة للإطلاق | أي وظيفة مطلوبة وغير منفذة تمنع الإطلاق |
| الحسابات والأدوار | أكد حدود المدير والمراجع، ومن ينشئ كل نوع حساب، ومن ينشر كل نوع محتوى | اختبارات صلاحيات موجبة وسالبة |
| الاختبارات | `QUIZ_MAX_ATTEMPTS` رقم موجب؛ `QUIZ_DURATION_MINUTES` رقم موجب أو اعتماد أن الأستاذ يحدد المدة دائمًا؛ `QUIZ_RESULT_VISIBILITY` واحدة من `IMMEDIATE`, `AFTER_WINDOW`, `AFTER_MANUAL_GRADING`; `QUIZ_INCOMPLETE_ATTEMPT_POLICY` واحدة من `AUTO_SUBMIT`, `CANCEL_COUNTED`, `CANCEL_FREE` | من دونها قد يرفض النظام بدء المحاولة |
| الرسائل | `MESSAGING_RATE_LIMIT_COUNT` و`MESSAGING_RATE_LIMIT_WINDOW_SECONDS` رقمان موجبان وفق سياسة المالك | من دونها قد يرفض النظام إرسال الرسائل |
| أمن الدخول | مهلة الجلسة والثوابت الأربعة `SESSION_IDLE_TIMEOUT_SECONDS`, `LOGIN_MAX_ATTEMPTS`, `LOGIN_WINDOW_SECONDS`, `LOGIN_LOCKOUT_SECONDS`؛ اعتماد حد كلمة المرور الحالي أو تغييره | إعدادات إلزامية للمصادقة |
| رفع الملفات | `UPLOAD_MAX_BYTES`، صيغ/أنواع الملفات المقبولة، وحدود PHP وخادم الويب المطابقة؛ هل يلزم فحص برمجيات ضارة قبل المراجعة؟ | الرفع يتوقف إذا لم يحدد الحد |
| السعة | عدد الطلاب عند الإطلاق وبعد سنة، عدد البثوث المتزامنة ومتوسط مدتها، حجم الملفات، أوقات الذروة | اختيار موارد الخادم وحدود التكلفة وخطة اختبار الحمل |
| الخصوصية والاحتفاظ | نسخة نهائية من سياسة الخصوصية والاستخدام، إقرار ولي الأمر إذا كان مطلوبًا، مدد الاحتفاظ بالرسائل والتسجيلات والحسابات والسجلات، ومسار طلب الحذف | يجب نشر النصوص وربط الإقرار قبل جمع بيانات حقيقية |
| النسخ والاستعادة | الوجهة الخارجية، التكرار، مدة الاحتفاظ، التشفير، المسؤول، RPO وRTO، وطريقة اختبار الاستعادة | جدول النسخ وخطة التعافي |
| مصفوفة الإطلاق | الصفوف والمواد المطلوب إدخالها يدويًا حسب منهج وزارة التربية والتعليم السودانية | تدخل بعد إنشاء المدير وقبل اختبار الطالب |

احفظ قائمة الصفوف والمواد من الإدارة في ملف تشغيل داخلي (اسم المرحلة، اسم الصف، المواد). لا تضعها في ترحيل قاعدة البيانات؛ القرار أن تدخل يدويًا. اعتمد أسماء صفوف المرحلة المتوسطة قبل إضافتها.

## المرحلة 2: اجتز فحوص المستودع وCI

نفّذ من نسخة العمل التي تحتوي التعديلات المقصودة. لا ترفع `.env` أو محتوى خاصًا أو نسخًا احتياطية. لاحظ أن الفحوص المحلية الساكنة لا تغني عن PostgreSQL وHTTP في GitHub Actions.

```bash
git status --short
git diff --check
php tests/password_policy.php
php tests/content_range_unit.php
php tests/quiz_policy_unit.php
for check in tests/static_phase{1..8}_checks.py; do python3 "$check" || exit 1; done
find app public database tests -name '*.php' -print0 | xargs -0 -n1 php -l
for file in public/assets/js/*.js; do node --check "$file" || exit 1; done
```

بعد مراجعة الفرق والتأكد أن `git status` لا يعرض أسرارًا أو ملفات بيانات، ارفع التغيير إلى فرع مراجعة في GitHub بالطريقة المعتمدة لفريقك. افتح نتيجة GitHub Actions لآخر commit وانتظر نجاح كل الخطوات، ومنها PostgreSQL migrations، اختبارات DB/HTTP، وفحص النسخ والاستعادة. إذا فشل أي اختبار: لا تدمج؛ افتح السجل، أصلح سبب الفشل، وادفع التغيير ثم أعد انتظار الـworkflow حتى ينجح. لا تعلن النجاح من الفحوص الساكنة وحدها.

**بوابة 1:** لا تنتقل قبل وجود commit معروف ونتيجة CI خضراء لذلك الـcommit. سجّل رقم/رابط الـcommit والـworkflow.

## المرحلة 3: جهّز بيئة ما قبل الإنتاج

أنشئ بيئة منفصلة عن الإنتاج، وقاعدة بيانات منفصلة، ونطاقًا فرعيًا تجريبيًا مثل `staging.<نطاقك>`. لا تستخدم بيانات طلاب حقيقية. طبّق خصائص الاستضافة التالية بغض النظر عن Linux أو خادم الويب:

1. PHP 8.4 أو أحدث، مع `pdo_pgsql`, `fileinfo`, `mbstring`، وعميل PostgreSQL الذي يوفر `pg_dump` و`pg_restore`.
2. PostgreSQL مدعوم، مع قاعدة ومستخدم للتطبيق بأقل صلاحيات لازمة. لا تستخدم مستخدم `postgres` كحساب التطبيق.
3. web root يشير حصريًا إلى مجلد `public/`. امنع تقديم `.env`, `.git`, `app/`, `database/`, `docs/`, `storage/` وأي ملفات مخفية.
4. TLS صالح بين الزائر والأصل. في Cloudflare اجعل وضع SSL/TLS هو **Full (strict)** بعد نجاح فحص شهادة الأصل. امنع cache لصفحات الجلسات وواجهات API والملفات الخاصة.
5. مجلد `PRIVATE_STORAGE_PATH` ومجلد النسخ خارج `public/`، قابلان للكتابة من مستخدم PHP فقط، وغير قابلين للفهرسة أو التنزيل المباشر من الويب.
6. سجلات PHP وخادم الويب وPostgreSQL خاصة ومحدودة الصلاحية والاحتفاظ. لا تسجل كلمات المرور أو رموز الدعوات أو مفاتيح Stream.

اكتب `.env` على الخادم خارج web root، ولا تنسخ `.env.example` بلا تعديل. أدخل الأسرار مباشرة بأداة آمنة/مدير أسرار، لا في أوامر محفوظة بسجل الطرفية. اضبط على الأقل:

```text
APP_ENV=production
APP_DEBUG=0
APP_URL=https://<عنوان-الموقع-المعتمد>
APP_TIMEZONE=Africa/Khartoum
SESSION_SECURE=1
SESSION_IDLE_TIMEOUT_SECONDS=<القيمة-المعتمدة>
LOGIN_MAX_ATTEMPTS=<القيمة-المعتمدة>
LOGIN_WINDOW_SECONDS=<القيمة-المعتمدة>
LOGIN_LOCKOUT_SECONDS=<القيمة-المعتمدة>
AUTH_THROTTLE_KEY=<سر-عشوائي-قوي-فريد>
AUDIT_RETENTION_DAYS=<القيمة-المعتمدة>
AUTH_ATTEMPT_RETENTION_DAYS=<القيمة-المعتمدة>
DB_CONNECTION=pgsql
DB_HOST=<مضيف-قاعدة-البيانات>
DB_PORT=5432
DB_DATABASE=<اسم-قاعدة-ما-قبل-الإنتاج>
DB_USERNAME=<مستخدم-التطبيق>
DB_PASSWORD=<سر-قاعدة-البيانات>
DB_SSLMODE=<وضع-TLS-المعتمد-حسب-مكان-قاعدة-البيانات>
PRIVATE_STORAGE_PATH=<مسار-خاص-خارج-public>
UPLOAD_MAX_BYTES=<الحد-المعتمد-بالبايت>
QUIZ_MAX_ATTEMPTS=<القيمة-المعتمدة>
QUIZ_DURATION_MINUTES=<القيمة-المعتمدة-إن-كانت-افتراضية>
QUIZ_RESULT_VISIBILITY=<خيار-معتمد>
QUIZ_INCOMPLETE_ATTEMPT_POLICY=<خيار-معتمد>
MESSAGING_RATE_LIMIT_COUNT=<القيمة-المعتمدة>
MESSAGING_RATE_LIMIT_WINDOW_SECONDS=<القيمة-المعتمدة>
STREAM_PROVIDER=cloudflare_stream
CLOUDFLARE_ACCOUNT_ID=<معرّف-الحساب>
CLOUDFLARE_API_TOKEN=<رمز-سري>
CLOUDFLARE_STREAM_CUSTOMER_CODE=<رمز-عميل-Stream>
```

إذا كانت ميزة الاشتراكات المستقبلية لا تستخدم، لا تضبطها كشرط لمنح محتوى الإطلاق؛ سياسة الإطلاق هي منحة وصول يدوية. تأكد أن PHP-FPM وخادم الويب يطبقان حد الرفع المعتمد نفسه. لا تختر `DB_SSLMODE` عشوائيًا؛ اتبع هل قاعدة البيانات محلية أم على مضيف منفصل ومتطلبات المزود.

## المرحلة 4: أنشئ المخطط والمدير والبيانات الدراسية

على بيئة ما قبل الإنتاج فقط، وبعد التأكد من أن `DB_DATABASE` يشير إلى القاعدة الصحيحة:

```bash
php database/migrate.php
php database/create_admin.php
```

الأمر الثاني تفاعلي ويطلب الاسم والبريد وكلمة المرور مرتين دون إظهارها. لا تنشئ مديرًا بكلمة مرور عبر SQL أو كلمة افتراضية. سجل الدخول كمدير، ثم:

1. أنشئ المراحل والصفوف والمواد المعتمدة يدويًا من واجهة إدارة المنهج.
2. أنشئ حسابات الاختبار للفريق، وامنح كل حساب الدور المطلوب فقط.
3. أرسل دعوة كل موظف من المنصة عبر قناة خاصة. روابط الدعوة حساسة وتنتهي خلال 48 ساعة؛ لا تلصقها في تذاكر عامة أو أدوات تحليلات.
4. سجّل طالب اختبار باختيار صف نشط. تحقق من ظهوره مرتبطًا بذلك الصف.
5. امنح الطالب الوصول يدويًا من المدير/المراجع؛ تحقق أنه لا يرى المحتوى قبل المنحة ويراه بعدها، وأن السحب يعيد منعه.

## المرحلة 5: نفّذ اختبار القبول اليدوي على المتصفح

استخدم متصفحات سطح المكتب والهاتف إن توفرت. اختبر كل حالة بحساب جديد أو سجّل خطوات ونتائج واضحة. لا يكفي أن تفتح الصفحة؛ نفّذ الإجراء وتأكد من نتيجة قاعدة البيانات أو العرض.

| الدور | جرّب هذه العمليات | النتيجة المطلوبة |
| --- | --- | --- |
| زائر | التسجيل، اختيار صف نشط، تسجيل الدخول والخروج، نسخ CSRF مفقود/منتهي | تسجيل الطالب لا يمنحه المحتوى تلقائيًا؛ تظهر رسائل مفهومة ولا تظهر تفاصيل الخادم |
| طالب بلا منحة | فتح مكتبة/درس/امتحان/اختبار، الوصول إلى رابط ملف خاص مباشرة | رفض العرض والتنزيل؛ لا يعمل الرابط المباشر ولا تظهر مفاتيح التخزين |
| طالب بمنحة | فتح المحتوى المصرح، تنزيل PDF مع Range، اختبار، رسالة لأستاذه المعين، دخول حصة في نافذتها | يسمح فقط بما منحه الدور والسياسة؛ النتيجة حسب إعداد الاختبار؛ الرسائل فردية |
| أستاذ | إدارة مادة مسندة وغير مسندة، رفع مورد، إنشاء سؤال، جدولة حصة، بدء بث | يسمح داخل الإسناد فقط؛ يمنع خارج الإسناد؛ لا يرى الأستاذ اعتماد محتواه بنفسه |
| مراجع محتوى | مراجعة واعتماد/رفض كتاب وسؤال وامتحان؛ محاولة تغيير أدوار وحسابات لا يحق له إدارتها | يراجع وينشر بحسب التفويض المعتمد؛ لا يتجاوز الصلاحية ولا يحصل دون حاجة على كشف بيانات الحسابات |
| مدير | إدارة الصفوف والمواد والحسابات والأدوار والوصول والمراجعة والحصص | يستطيع العمليات المقررة؛ النظام يمنع تعطيل/إزالة آخر مدير نشط |
| جميع الأدوار | الهاتف، اتجاه RTL، الروابط، رسائل الخطأ، زر الرجوع، تحميل الصفحة، `/health` | لا تداخل أفقي أساسي ولا كسر للتخطيط؛ health يكشف حالة عامة فقط |

اختبر الاختبار بحالات: قبل الإعداد/بعده، بلوغ حد المحاولات، انتهاء المدة، محاولة غير مكتملة، وموعد إظهار النتيجة لكل من الطالب والأستاذ. اختبر رسالة خارج نافذة الحد المعتمد. أي اختبار غير ممكن سجّل سببه كـ**غير مختبر** وليس نجاحًا.

استخدم نموذج التسجيل في نهاية هذا الملف لكل عيب. أوقف الانتقال إذا فشل تسجيل الدخول أو الصلاحيات أو عرض ملف خاص أو تطبيق المنحة أو المصادقة أو الاختبار.

## المرحلة 6: اختبر Cloudflare Stream بالبث الحقيقي

يحتاج هذا الاختبار حساب Cloudflare وإعداد Stream. لا تستخدم فيديو طالب حقيقي.

1. أنشئ token بصلاحيات Stream Read/Write اللازمة فقط، وضعه في أسرار بيئة ما قبل الإنتاج. لا تضعه في `.env` محلي يُرفع إلى Git.
2. أنشئ حصة مباشرة من حساب أستاذ مخول، واستخرج مفتاح/بيانات الإرسال. تأكد أن المفتاح يظهر مرة واحدة للأستاذ ولا يحفظ في صفحة عامة أو قاعدة المنصة.
3. أرسل بثًا تجريبيًا من OBS بمدة قصيرة بعد بدء نافذة الحصة. تحقق أن الطالب المخول فقط يستطيع الانضمام وأن رابط المشاهدة موقّع ومن المسار المحمي.
4. أنهِ البث. انتظر اكتمال التسجيل ومزامنته، ثم تحقق أن التسجيل لا يظهر قبل أن يصبح جاهزًا وموعد إتاحته.
5. جرّب حساب طالب غير مخول، رابطًا منتهيًا، وحصة قبل/بعد نافذتها؛ يجب رفض المشاهدة.
6. أوقف المفتاح التجريبي عند نهاية التجربة، وراجع سجلات Cloudflare والخادم بحثًا عن أسرار أو روابط طويلة العمر.
7. قارن عدد البثوث المتزامنة المجرب بخطة السعة المعتمدة. إذا لم تعتمد السعة أو التكلفة، اترك الإطلاق العام متوقفًا.

## المرحلة 7: النسخ الاحتياطي والاستعادة

اعتمد أولًا الوجهة الخارجية والتكرار والاحتفاظ والتشفير وRPO/RTO. اختبر إنشاء نسخة محلية مسجلة على قاعدة ما قبل الإنتاج:

```bash
php database/backup.php
```

افحص سجل التشغيل للتأكد من حالة النسخة والبصمة والحجم. انقل النسخة إلى وجهة خارجية مشفرة بواسطة إعداد النقل المعتمد؛ لا تضع النسخة بجوار قاعدة الإنتاج فقط. تحقق أن ملف النسخة ليس متاحًا عبر HTTP.

نفّذ تمرين الاستعادة على قاعدة مؤقتة منفصلة كما هو موثق في `docs/OPERATIONS_BACKUP_RESTORE.md`؛ استخدم اسم نسخة فعليًا مطبوعًا من أمر النسخ، واسم قاعدة مؤقتة تملكها. لا تشغّل أمر الاستعادة على قاعدة الإنتاج في هذا التمرين. النجاح يتطلب رمز خروج ناجحًا، وجود الترحيلات المتوقعة، وتسجيل `RESTORED` وبصمة مطابقة. وثّق الوقت والمدة والنتيجة وقارن مدة الاستعادة بهدف RTO.

## المرحلة 8: إطلاق تجريبي محدود

لا تفتح الموقع للعامة بعد. انشر نفس commit الذي اجتاز CI وUAT إلى بيئة ما قبل الإنتاج. تحقق من:

```bash
curl --fail --show-error https://<عنوان-ما-قبل-الإنتاج>/health
```

يجب أن تكون الحالة `200` و`{"status":"ok"}` دون تفاصيل اتصال. راجع أن شهادة HTTPS سليمة، وأن `.env` والملفات الخاصة غير قابلة للطلب عبر HTTP، وأن صفحات الدخول والاختبار والحسابات لا تُخزن في CDN. راجع سجلات 4xx/5xx، وأعد اختبار دعوة جديدة بعد التأكد من `APP_URL` الصحيح.

شغّل مجموعة محدودة من المدراء والأساتذة والطلاب التجريبيين لأسبوع/مدة يحددها المالك، وراقب الأخطاء وسعة التخزين والبث والنسخ. هذه المدة يجب أن تعتمدها الجهة؛ لا تعتبرها اختبار حمل علميًا. إذا ظهرت مشكلة صلاحية أو تسرب ملف أو فشل نسخة، أوقف التجربة وأصلحها ثم أعد الاختبار.

## بوابة الإطلاق العام

لا تحول DNS إلى الإنتاج ولا تعلن الرابط حتى تسجل جميع البنود التالية كناجحة:

- [ ] نطاق SRS للإطلاق موقع ومعروف، وكل وظيفة مطلوبة منفذة أو لها قبول صريح بالتأجيل.
- [ ] جميع قرارات الإطلاق المؤثرة معتمدة وقيم البيئة مطابقة لها.
- [ ] CI أخضر على commit النشر نفسه.
- [ ] لا توجد أسرار أو ملفات بيانات في Git؛ `git diff --check` نظيف.
- [ ] جميع ترحيلات `001` إلى `010` مطبقة ومتحقق منها على قاعدة ما قبل الإنتاج.
- [ ] HTTPS وCloudflare Full (strict) وweb root `public/` واختبار منع الوصول للملفات الداخلية ناجح.
- [ ] مدير أول آمن، بيانات المناهج أُدخلت، والحسابات التجريبية ذات أدوار صحيحة.

- [ ] Cloudflare Stream live وrecorded اجتازا تجربة فعلية بصلاحيات صحيحة.
- [ ] نسخة احتياطية خارجية موجودة وتمت استعادتها على قاعدة معزولة ضمن RTO المعتمد.
- [ ] سياسات الخصوصية والاستخدام والموافقات ظاهرة ومقبولة حسب قرار المالك.
