# خطة إنهاء العمل قبل استئجار الخادم

## الهدف

إنهاء ما يمكن إنجازه وتجربته دون خادم إنتاج، وتجهيز ملف تسليم يثبت حالة المشروع. في نهاية الخطة يمكن أن تقول للمدير: «الكود وقرارات التشغيل وإعداد الخدمات جاهزة؛ المتبقي توفير خادم الإنتاج لإجراء النشر والاختبار النهائي». لا تستخدم هذه العبارة قبل إغلاق الشروط أدناه.

لا يمكن قبل وجود الخادم إثبات DNS وTLS على الأصل، أو أداء المنصة على موارد الإنتاج، أو إتمام اختبار قبول على رابط فعلي. لذلك تعني «جاهز للنشر» أن النسخة اجتازت CI واختبارات ما قبل الإنتاج وأن أسرار وخطط التشغيل جاهزة، لا أن الإطلاق العام تم.

## شرط ادعاء أن الخادم هو المتبقي الوحيد

يجب إغلاق جميع العناصر التالية قبل إعداد خطاب الحالة:

1. قرارات الإطلاق المحددة في القسم الأول معتمدة كتابةً من المدير/مالك المنتج.
2. صلاحية الوصول لمستودع GitHub ونتيجة CI ناجحة على commit الإصدار.
3. حساب Cloudflare والنطاق جاهزان؛ Stream مفعّل، API Token مناسب محفوظ بأمان، واختبار إنشاء/إنهاء بث وتسجيل تجريبي ناجح.
4. مزود أو حساب تخزين النسخ الخارجية مختار، وسياسة النسخ والاستعادة معتمدة، واختبار استعادة على قاعدة معزولة ناجح.
5. نصوص الخصوصية والاستخدام والموافقة المطلوبة مستلمة ومراجعة ومجهزة للإضافة على الموقع.
6. قائمة مراحل وصفوف ومواد الإطلاق معتمدة وجاهزة للإدخال من حساب المدير.
7. قبول يدوي على نسخة ما قبل الإنتاج/التشغيل المحلي مكتمل، والعيوب الحرجة مغلقة.

إذا لم يتوفر Cloudflare أو مخزن النسخ أو موافقات السياسات، فاكتب أنها **متطلبات خارجية باقية مع الخادم**، ولا تقل إن الخادم هو المتبقي وحده.

## المرحلة 1: اجتماع حسم قرارات الإطلاق

اعرض الجدول على المدير/مالك المنتج. اكتب قيمة أو جوابًا لكل سطر، واسم المعتمد وتاريخ الاعتماد. لا تدخل قيمًا افتراضية من CI؛ هذه قيم اختبار فقط.

| القرار المطلوب | المطلوب من المدير |
| --- | --- |
| نطاق SRS | اعتماد ما يدخل الإصدار الأول وما يؤجل: توليد AI، بوابة ولي الأمر، اللعبة، تطبيق الهاتف، وأي تقارير إدارية ناقصة |
| الأدوار | تحديد صلاحيات المدير والمراجع بدقة، ومن يسمح له بإنشاء حساب مدير/مراجع/أستاذ، ومن يراجع وينشر كل نوع محتوى |
| الاختبارات | تحديد حد المحاولات، المدة الافتراضية أو اعتماد أن الأستاذ يحددها، توقيت عرض النتيجة، والتصرف عند عدم الإكمال |
| الرسائل | تحديد عدد الرسائل المسموح في فترة زمنية، ومدة الاحتفاظ والحذف |
| الحماية | اعتماد مهلة الجلسة، حد محاولات الدخول ونافذة العد وزمن القفل، سياسة كلمة المرور والاحتفاظ بسجلات التدقيق والدخول |
| الملفات | اعتماد أقصى حجم، الصيغ المقبولة، هل يلزم فحص مضاد للبرمجيات الضارة، ووجهة التخزين الخاصة |
| السعة | عدد المستخدمين المتوقع عند الإطلاق وبعد سنة، بثوث متزامنة ومتوسط مدتها، واستخدام الذروة المتوقع |
| Cloudflare | تأكيد حساب Cloudflare، النطاق، Stream، مسؤول الأسرار والتكلفة، وسياسة الاحتفاظ بالتسجيلات |
| النسخ | اختيار مخزن خارجي، التكرار والاحتفاظ والتشفير، مسؤول الاستعادة، هدف فقد البيانات المقبول RPO، ووقت الاستعادة المقبول RTO |
| الخصوصية | تسليم النص النهائي لسياسات الخصوصية والاستخدام وموافقة ولي الأمر إن كانت لازمة، ومدد الاحتفاظ بالبيانات |
| المنهج | اعتماد أسماء المراحل والصفوف والمواد المطلوبة للإطلاق من منهج وزارة التربية والتعليم السودانية |

احفظ محضر الاعتماد ضمن ملفات الشركة، وليس داخل Git إذا احتوى بيانات حساسة. حدّث `docs/OPEN_DECISIONS.md` بالإجابات غير السرية المعتمدة.

## المرحلة 2: جهّز نسخة إصدار قابلة للمراجعة

1. افتح فرق التعديلات في المستودع. تأكد من عدم وجود `.env` أو أسرار أو بيانات طلاب أو ملفات رفع/نسخ احتياطية ضمن التغيير.
2. اعرض `git status --short` وراجع كل ملف متغير، بما فيه حالة أي submodule. لا تحذف تغييرات أو submodule لمجرد أنه ظاهر في الحالة.
3. نفّذ:

```bash
git diff --check
php tests/password_policy.php
php tests/content_range_unit.php
php tests/quiz_policy_unit.php
for check in tests/static_phase{1..8}_checks.py; do python3 "$check" || exit 1; done
find app public database tests -name '*.php' -print0 | xargs -0 -n1 php -l
for file in public/assets/js/*.js; do node --check "$file" || exit 1; done
```

4. ادفع commit إلى فرع مراجعة بالطريقة المعتادة. راجع GitHub Actions وانتظر نجاح workflow كاملًا: ترحيلات PostgreSQL، تكامل DB/HTTP، الصلاحيات، الملفات الخاصة، والنسخ والاستعادة.
5. إذا فشل CI، لا تعتبر النسخة جاهزة. أصلح الفشل وادفع commit جديدًا حتى يصبح workflow أخضر.
6. سجّل SHA ورابط commit ورابط workflow ووقتهما في تقرير التسليم.

## المرحلة 3: اختبر إعداد الخدمات غير المتعلقة بالخادم

### Cloudflare Stream

1. تأكد من أن نطاق الشركة في حساب Cloudflare الصحيح.
2. فعّل Cloudflare Stream وراجع التكلفة وشروط الاحتفاظ بالتسجيلات مع المدير.
3. أنشئ API Token بصلاحيات Stream المطلوبة فقط. احفظه في مدير أسرار الشركة؛ لا ترسله في المحادثة أو البريد العادي ولا ترفعه إلى Git.
4. ضع القيم في بيئة محلية معزولة لاستخدام الاختبار (`STREAM_PROVIDER`, `CLOUDFLARE_ACCOUNT_ID`, `CLOUDFLARE_API_TOKEN`, `CLOUDFLARE_STREAM_CUSTOMER_CODE`).
5. أنشئ حصة تجريبية، ابدأ بث OBS قصيرًا، اختبر رابط المشاهدة الموقّع، أنه البث وانتظر مزامنة التسجيل، ثم اختبر منع مستخدم غير مخول.
6. ألغِ أو احذف مدخل الاختبار، وأعد إصدار Token إن تم كشفه أو مشاركته خطأً. أرفق نتيجة الاختبار دون إظهار المفاتيح.

إذا تعذر الاختبار لأن الموقع لا يعمل من الإنترنت دون خادم، اختبر واجهة Stream وحسابها من أداة معتمدة، وسجّل تكامل التطبيق بوصفه «ينتظر رابط staging على الخادم». عندها لا تقل إن Cloudflare اختُبر end-to-end.

### النسخ الاحتياطي خارج الخادم

1. اعتمد المدير وجهة التخزين الخارجية والحساب المسؤول عنها وسياسة الاحتفاظ والتشفير.
2. جهّز وسيلة نقل آمنة ومقيدة من خادم التطبيق إلى مخزن النسخ. لا تحفظ النسخة على نفس قرص قاعدة البيانات فقط.
3. على PostgreSQL اختبار معزول، نفّذ `php database/backup.php` ثم تحقق من سجل الحالة والحجم وSHA-256.
4. انقل النسخة إلى الوجهة الخارجية وفق الإجراء المعتمد، وتحقق من وجودها وعدم إتاحتها عبر الويب.
5. أنشئ قاعدة استعادة مؤقتة ونفذ تمرين الاستعادة كما في `docs/OPERATIONS_BACKUP_RESTORE.md`. لا تستخدم قاعدة الإنتاج لهذا الاختبار.
6. سجل زمن النسخ والاستعادة، وطابقه مع RPO/RTO المعتمد. أرفق إثباتًا منقحًا لا يحتوي مفاتيح أو بيانات مستخدمين.

إذا لم يوجد حساب/مخزن خارجي الآن، فهذه متطلب خارجي ثانٍ؛ الخادم ليس المتبقي الوحيد.

## المرحلة 4: اختبار الموقع يدويًا قبل الخادم

استخدم PostgreSQL اختبارية وفق آلية CI أو بيئة محلية مسموحًا بها، وحسابات وهمية فقط. اتبع مصفوفة الأدوار في `docs/FINAL_RELEASE_RUNBOOK.md`، وأكمل على الأقل:

- التسجيل الذاتي واختيار صف، ومنع وصول الطالب للمحتوى قبل المنحة اليدوية، ثم السماح بعد المنحة ومنع الوصول بعد سحبها.
- إدخال مرحلة وصف وصفوف ومواد، وإسناد مادة لأستاذ.
- رفع PDF خاص، اعتماده/رفضه، وتجربة Range، ومحاولة فتح الملف مباشرة دون صلاحية.
- إنشاء سؤال/اختبار ومراجعته، وحالات حد المحاولات والمدة والنتيجة ومحاولة غير مكتملة.
- إنشاء حصة ورسالة فردية، واختبار قواعد الصلاحية ومعدل الرسائل.
- اختبار المدير والمراجع والأستاذ والطالب والحساب غير المخول؛ سجّل كل نجاح وفشل.
- اختبار الواجهة بالعربية RTL على شاشة هاتف وسطح مكتب، وتسجيل أي تعطل أو قص/تمدد.

لكل اختبار سجّل: التاريخ، commit، البيئة، الدور، الخطوات، المتوقع، الفعلي، نجاح/فشل/غير مختبر، والعيب المسؤول عنه. لا تسجل كلمات مرور أو بيانات طالب حقيقية.

## المرحلة 5: جهّز ملف المدير

أنشئ تقريرًا PDF أو مستندًا داخليًا يحتوي فقط على:

1. الهدف والنطاق المعتمد للإصدار الأول.
2. رقم commit ورابطه ونتيجة CI الخضراء.
3. ملخص الوظائف التي تم تنفيذها ومصفوفة الاختبارات اليدوية.
4. إثبات نجاح اختبار Stream والنسخ الخارجي والاستعادة، أو وصفها بدقة كمتطلبات باقية.
5. قرارات التشغيل والسياسات التي اعتمدها المدير وتاريخ الاعتماد.
6. قائمة «متبقي قبل الإطلاق» مقسمة إلى: توفير الخادم، إعداد DNS/TLS، إعداد الأسرار على الخادم، النشر، اختبارات الأصل، مراقبة الإنتاج.
7. مخاطر معروفة أو وظائف خارج النطاق وافق المدير على تأجيلها.

استخدم الصياغة المطابقة للحالة:

- إذا أغلقت كل ما سبق: **«الكود وCI واختبارات ما قبل الإنتاج والخدمات الخارجية جاهزة. المتبقي توفير خادم الإنتاج، ثم ربط DNS/TLS والنشر واجتياز فحوص الأصل.»**
- إذا لم يُجهز Stream أو التخزين أو السياسات: **«العمل البرمجي متقدم، لكن الإطلاق ينتظر الخادم وهذه المتطلبات الخارجية/القرارات المذكورة.»**

لا تقل إن كل متطلبات SRS اكتملت إلا إذا كانت كل وظيفة مطلوبة للإطلاق مجرّبة ومقبولة. أي مطلب مؤجل يجب أن يظهر كتأجيل معتمد.

## المرحلة 6: ما ينفذ فور توفير الخادم

بعد أن توفر الشركة خادمًا ونطاقًا وتفويضًا:

1. أنشئ بيئة staging على الخادم أولًا، مع PHP 8.4+ و`pdo_pgsql` و`fileinfo` و`mbstring` وأدوات `pg_dump` و`pg_restore`.
2. اجعل web root `public/` فقط. أنشئ PostgreSQL وقاعدة/مستخدم تطبيق محدودًا، ومجلد ملفات خاص خارج web root ومجلد نسخ مقيدًا.
3. ضع `.env` خارج web root عبر مدير أسرار؛ اضبط الإنتاجية وHTTPS وقيم القرارات المعتمدة ومعلومات Stream وقاعدة البيانات والتخزين.
4. طبّق ترحيلات `001` إلى `010` مرة واحدة على قاعدة staging ثم أنشئ المدير تفاعليًا عبر `php database/create_admin.php`.
5. اربط النطاق من Cloudflare بسجلات Vercel/الخادم التي يحددها مزود الاستضافة. اختبر TLS، ثم فعّل Cloudflare Full (strict) إذا كان مسار الأصل يدعمه. لا تحول DNS قبل نجاح staging.
6. أعد اختبارات المتصفح وStream والملفات الخاصة والنسخ والاستعادة على staging؛ اختبر من هاتف وشبكات مختلفة.
7. بعد موافقة المدير، خذ نسخة، انشر نفس commit المجتاز، اختبر `/health` والتسجيل والصلاحيات، ثم افتح الوصول تدريجيًا.
8. راقب الأخطاء والنسخ والاستهلاك واتبع خطة رجوع متفقًا عليها.
